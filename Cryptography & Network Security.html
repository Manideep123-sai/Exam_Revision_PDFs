Modular Arithmetic

Modular arithmetic is a system where numbers "wrap around" after reaching the modulus n. We write a ≡ b (mod n) when n divides (a − b), i.e., both leave the same remainder when divided by n.

Core Definition: If a = qn + r, where 0 ≤ r < n, then a mod n = r.

Key Properties (all mod n):

  • (a + b) mod n = [(a mod n) + (b mod n)] mod n
  • (a − b) mod n = [(a mod n) − (b mod n) + n] mod n
  • (a × b) mod n = [(a mod n) × (b mod n)] mod n
  • Commutativity, Associativity, Distributivity all hold
  • Additive inverse of a is (n − a) mod n
  • Multiplicative inverse of a mod n exists if and only if gcd(a, n) = 1
Core Notation
a ≡ b (mod n) ⟺ n | (a − b) ⟺ a mod n = b mod n
Negative: −a mod n = n − (a mod n)
Example: −3 mod 7 = 4 (since 7 − 3 = 4)
✦ Worked Example
Q: Find (17 × 13) mod 7
Step 1: 17 mod 7 = 3
Step 2: 13 mod 7 = 6
Step 3: (3 × 6) mod 7 = 18 mod 7 = 4
∴ (17 × 13) mod 7 = 4
✦ Negative Modulo
Q: −11 mod 4 = ?
Method: 11 mod 4 = 3, so −11 mod 4 = 4 − 3 = 1
Check: −11 = (−3)×4 + 1 ✓
∴ −11 mod 4 = 1
Euclidean Algorithm — GCD

The Euclidean Algorithm computes gcd(a, b) using repeated division. The key insight: gcd(a, b) = gcd(b, a mod b). Terminates when remainder = 0; the last non-zero remainder is the GCD.

Two integers a, b are coprime / relatively prime if gcd(a, b) = 1. Essential for RSA and CRT.

Algorithm
gcd(a, b) = gcd(b, a mod b) ← recursive step
gcd(a, 0) = a ← base case
Time complexity: O(log min(a,b))
✦ gcd(252, 105)
252 = 2 × 105 + 42 → gcd(105, 42)
105 = 2 × 42 + 21 → gcd(42, 21)
42 = 2 × 21 + 0 → gcd(21, 0)
∴ gcd(252, 105) = 21
✦ gcd(48, 18)
48 = 2 × 18 + 12 → gcd(18, 12)
18 = 1 × 12 + 6 → gcd(12, 6)
12 = 2 × 6 + 0 → gcd(6, 0)
∴ gcd(48, 18) = 6
Extended Euclidean Algorithm

Finds integers x and y such that ax + by = gcd(a, b) — Bézout's Identity. Most importantly, finds the modular multiplicative inverse: ax ≡ 1 (mod m). Critical for RSA key generation and CRT.

Bézout's Identity
ax + by = gcd(a, b) for integers x, y
Modular inverse: ax ≡ 1 (mod m) when gcd(a, m) = 1
Inverse = x adjusted to positive: if x < 0, use x + m
✦ Find 3⁻¹ mod 11
Need: 3x ≡ 1 (mod 11). Apply Ext. Euclidean to 11, 3:
11 = 3×3 + 2 → 2 = 11 − 3×3
3 = 1×2 + 1 → 1 = 3 − 1×2
Back-sub: 1 = 3 − (11 − 3×3) = 4×3 − 11
So 3×4 ≡ 1 (mod 11)
∴ 3⁻¹ mod 11 = 4 (3×4=12≡1 mod 11 ✓)
✦ Find 7⁻¹ mod 26 (used in affine cipher)
26 = 3×7 + 5 → 5 = 26 − 3×7
7 = 1×5 + 2 → 2 = 7 − 1×5
5 = 2×2 + 1 → 1 = 5 − 2×2
Back-sub: 1 = 5 − 2(7−5) = 3×5 − 2×7
1 = 3(26−3×7) − 2×7 = 3×26 − 11×7
So: −11×7 ≡ 1 (mod 26), x = −11 + 26 = 15
∴ 7⁻¹ mod 26 = 15 (7×15=105=4×26+1 ✓)
✦ Tabular Method — Find 17⁻¹ mod 43
| a | b | q | r | s | t |
| 43 | 17 | 2 | 9 | 1 | 0 |
| 17 | 9 | 1 | 8 | 0 | 1 |
| 9 | 8 | 1 | 1 | 1 | -1 | (s = prev_s - q×curr_s)
| 8 | 1 | 8 | 0 | -1 | 2 |
gcd=1, inverse t-value for row with r=1 → t = 2 (but sign needs check)
Actually: 1 = 9 − 8 = 9 − (17−9) = 2×9 − 17 = 2(43−2×17) − 17 = 2×43 − 5×17
So −5×17 ≡ 1 (mod 43), x = −5 + 43 = 38
∴ 17⁻¹ mod 43 = 38 (17×38=646=15×43+1 ✓)
Fermat's Little Theorem

If p is prime and gcd(a, p) = 1, then a^(p−1) ≡ 1 (mod p).

Applications:

  • Compute large modular exponentiations: reduce exponent mod (p−1)
  • Primality testing (Fermat primality test)
  • Modular inverse: a⁻¹ ≡ a^(p−2) (mod p) — only when p is prime
  • RSA correctness proof

Carmichael numbers: Composite numbers that pass the Fermat test for all a coprime to n (e.g., 561 = 3×11×17). These are called Fermat pseudoprimes.

Fermat's Little Theorem
a^(p−1) ≡ 1 (mod p) [p prime, gcd(a,p)=1]
Equivalent form: a^p ≡ a (mod p)
Inverse form: a⁻¹ ≡ a^(p−2) (mod p) [only if p prime]
✦ Compute 3¹⁰⁰ mod 7
p = 7 (prime), so 3^6 ≡ 1 (mod 7) by Fermat
100 = 6 × 16 + 4
3^100 = (3^6)^16 × 3^4 ≡ 1^16 × 81 (mod 7)
81 mod 7 = 81 − 11×7 = 81 − 77 = 4
∴ 3^100 mod 7 = 4
✦ Compute 2^¹⁰⁰⁰ mod 13
p = 13, so 2^12 ≡ 1 (mod 13) by Fermat
1000 = 12 × 83 + 4
2^1000 ≡ (2^12)^83 × 2^4 ≡ 1 × 16 (mod 13)
16 mod 13 = 3
∴ 2^1000 mod 13 = 3
✦ Find 5⁻¹ mod 7 using Fermat
5^(7−2) mod 7 = 5^5 mod 7
5^1≡5, 5^2=25≡4, 5^4=4²=16≡2 (mod 7)
5^5 = 5^4 × 5 ≡ 2×5 = 10 ≡ 3 (mod 7)
∴ 5⁻¹ mod 7 = 3 (5×3=15≡1 mod 7 ✓)
Euler's Theorem & Totient Function φ(n)

Euler's Totient φ(n) counts integers from 1 to n that are coprime to n.

  • φ(1) = 1
  • φ(p) = p − 1 for prime p
  • φ(p^k) = p^(k−1)(p−1)
  • φ(mn) = φ(m)×φ(n) when gcd(m,n) = 1 (multiplicative property)
  • φ(pq) = (p−1)(q−1) for distinct primes p, q ← used directly in RSA!

Euler's Theorem: Generalizes Fermat. For gcd(a, n) = 1: a^φ(n) ≡ 1 (mod n). When n is prime, φ(n) = n−1, reducing to Fermat.

General formula: φ(n) = n × ∏(1 − 1/pᵢ) for each prime pᵢ dividing n.

Euler's Theorem
a^φ(n) ≡ 1 (mod n) [gcd(a,n) = 1]

φ(12) = 12 × (1−½) × (1−⅓) = 4
φ(30) = 30 × (1−½) × (1−⅓) × (1−⅕) = 8
φ(p^k) = p^(k−1)(p−1) e.g. φ(8) = φ(2³) = 2²(2−1) = 4
✦ Compute various φ values
φ(7) = 6 [prime → p−1]
φ(12) = φ(4)×φ(3) = 2×2 = 4
φ(36) = φ(4)×φ(9) = 2×6 = 12
φ(77) = φ(7×11) = 6×10 = 60
φ(100)= φ(4)×φ(25) = 2×20 = 40
Verify: 5^4 mod 12 = 625 mod 12 = 1 ✓ (φ(12)=4)
✦ Compute 7^222 mod 10
φ(10) = φ(2)×φ(5) = 1×4 = 4
gcd(7,10)=1, so 7^4 ≡ 1 (mod 10)
222 = 4×55 + 2
7^222 = (7^4)^55 × 7^2 ≡ 1 × 49 ≡ 9 (mod 10)
∴ 7^222 mod 10 = 9
Chinese Remainder Theorem (CRT)

CRT: if n₁, n₂, ..., nₖ are pairwise coprime, then the system of congruences has a unique solution mod N = n₁×n₂×...×nₖ.

Steps:

  1. Compute N = n₁ × n₂ × ... × nₖ
  2. For each i: Nᵢ = N / nᵢ
  3. For each i: Mᵢ = Nᵢ⁻¹ mod nᵢ (Extended Euclidean)
  4. x = (Σ aᵢ × Nᵢ × Mᵢ) mod N

Used in RSA speedup (CRT form), number theory, and computer architecture.

CRT Formula
System: x ≡ a₁(mod n₁), x ≡ a₂(mod n₂), ..., x ≡ aₖ(mod nₖ)
N = n₁×n₂×...×nₖ, Nᵢ = N/nᵢ, Mᵢ = Nᵢ⁻¹ mod nᵢ
x = (Σ aᵢ · Nᵢ · Mᵢ) mod N
✦ Example 1 — x≡2(mod3), x≡3(mod5), x≡2(mod7)
N = 3×5×7 = 105
N₁=35: M₁=35⁻¹ mod 3 → 35 mod 3=2, 2⁻¹ mod 3=2 ∴ M₁=2
N₂=21: M₂=21⁻¹ mod 5 → 21 mod 5=1, 1⁻¹ mod 5=1 ∴ M₂=1
N₃=15: M₃=15⁻¹ mod 7 → 15 mod 7=1, 1⁻¹ mod 7=1 ∴ M₃=1
x = (2×35×2 + 3×21×1 + 2×15×1) mod 105
= (140 + 63 + 30) mod 105 = 233 mod 105 = 23
∴ x = 23 Check: 23%3=2✓ 23%5=3✓ 23%7=2✓
✦ Example 2 — x≡1(mod2), x≡2(mod3), x≡3(mod5)
N = 30, N₁=15, N₂=10, N₃=6
M₁ = 15⁻¹ mod 2 = 1⁻¹ mod 2 = 1
M₂ = 10⁻¹ mod 3 = 1⁻¹ mod 3 = 1
M₃ = 6⁻¹ mod 5 = 1⁻¹ mod 5 = 1
x = (15 + 20 + 18) mod 30 = 53 mod 30 = 23
∴ x = 23 Check: 23%2=1✓ 23%3=2✓ 23%5=3✓
✦ Example 3 — x≡3(mod4), x≡5(mod7)
N = 28, N₁=7, N₂=4
M₁ = 7⁻¹ mod 4: 7 mod 4=3, 3⁻¹ mod 4: 3×3=9≡1 → M₁=3
M₂ = 4⁻¹ mod 7: 4×2=8≡1 → M₂=2
x = (3×7×3 + 5×4×2) mod 28 = (63 + 40) mod 28 = 103 mod 28 = 19
∴ x = 19 Check: 19%4=3✓ 19%7=5✓
Discrete Logarithm Problem

Given prime p, generator g (primitive root mod p), and y = g^x mod p, the DLP is: find x. Computationally infeasible for large p — underpins DH, ElGamal, DSA.

Primitive Root g: g is a primitive root mod p if {g¹, g², ..., g^(p−1)} = {1, 2, ..., p−1}. Every prime has ≥1 primitive root. Powers of g cover all non-zero residues.

Discrete Logarithm
Easy direction: y = g^x mod p (fast exponentiation)
Hard direction: find x given g, p, y (DLP — basis of security)
Notation: x = log_g(y) mod p (also written ind_g(y))
✦ Find log₂(9) mod 11
Compute powers of 2 mod 11:
2¹≡2, 2²≡4, 2³≡8, 2⁴=16≡5, 2⁵=32≡10, 2⁶=64≡9
∴ log₂(9) mod 11 = 6 (2⁶ ≡ 9 mod 11)
✦ Check if 2 is a primitive root mod 11
Powers of 2 mod 11: 2,4,8,5,10,9,7,3,6,1 → all 10 distinct values!
∴ 2 is a primitive root mod 11 ✓

DES — Data Encryption Standard

DES was developed by IBM, standardized by NIST in 1977. Uses a Feistel network: block split into two halves; one half processed through round function f with key, XORed with the other, then halves swap. Decryption uses same structure with reversed subkeys.

Parameters: Block = 64 bits | Key input = 64 bits (56 effective + 8 parity) | Rounds = 16

DES Round Function f(R, K):

  1. Expansion E: 32-bit R → 48 bits (some bits repeated)
  2. Key Mix: XOR with 48-bit round subkey Kᵢ
  3. S-box Substitution: 8 S-boxes, 6→4 bits each (48→32 bits). Non-linearity source.
  4. P-box Permutation: 32-bit fixed permutation. Diffusion source.

Status: Broken in 1998 (EFF Deep Crack). Replaced by AES. 3DES was interim.

Feistel Round Structure
Lᵢ = R_{i-1}
Rᵢ = L_{i-1} ⊕ f(R_{i-1}, Kᵢ)

Subkeys: K₁, K₂, ..., K₁₆ for encryption
Decryption: same circuit, subkeys in reverse K₁₆, ..., K₁
3DES-EDE (2-key): C = E_K1(D_K2(E_K1(P)))
3DES (3-key): C = E_K3(D_K2(E_K1(P)))

AES — Advanced Encryption Standard (Rijndael)

Selected by NIST in 2001. AES is a Substitution-Permutation Network (SPN) — unlike DES, the entire 128-bit block is processed every round. Block is organized as a 4×4 byte state matrix.

Parameters: Block = always 128 bits | Keys = 128/192/256 bits | Rounds = 10/12/14

Four Round Operations:

  1. SubBytes: Each byte replaced using a 16×16 S-box. Provides confusion (non-linearity). S-box = GF(2⁸) inverse + affine transform. Resists differential/linear cryptanalysis.
  2. ShiftRows: Row 0: no shift. Row 1: left 1. Row 2: left 2. Row 3: left 3. Provides inter-column diffusion.
  3. MixColumns: Each column multiplied by fixed matrix over GF(2⁸). Provides diffusion within columns. Skipped in final round!
  4. AddRoundKey: XOR state with round key (expanded from key schedule). Only step using the key directly.

Key Schedule: 128-bit key → 44 words (32-bit) = 11 round keys. Uses RotWord, SubWord, XOR with Rcon[i] for each 4th word.

AES-128 Round Structure
Initial: AddRoundKey(K₀)
Rounds 1–9: SubBytes → ShiftRows → MixColumns → AddRoundKey(Kᵢ)
Round 10 (Final): SubBytes → ShiftRows → AddRoundKey(K₁₀) ← No MixColumns!

Decryption inverses: InvShiftRows → InvSubBytes → AddRoundKey → InvMixColumns
Key schedule: W[4i+0] = W[4i-4] ⊕ SubWord(RotWord(W[4i-1])) ⊕ Rcon[i]
AES Round Operations on 4×4 State Matrix
⚠️ DES vs AES — Key Differences
DES: Feistel (only half-block per round), 64-bit block, 56-bit key, broken.
AES: SPN (full block every round), always 128-bit block, 128/192/256-bit key, secure.
AES S-box: mathematically constructed, no hidden backdoor.
AES: ~6× faster than DES in software.

Block Cipher Modes of Operation

Block ciphers process fixed-size blocks. Modes define how to handle multiple blocks (and handle IV, error propagation, parallelism).

Mode Encrypt Decrypt Key Properties
ECB
Electronic Codebook		 Cᵢ = E(K, Pᵢ) Pᵢ = D(K, Cᵢ) Same P→same C. No IV. Reveals patterns. INSECURE.
CBC
Cipher Block Chaining		 Cᵢ = E(K, Pᵢ⊕Cᵢ₋₁) Pᵢ = D(K, Cᵢ)⊕Cᵢ₋₁ Needs IV (C₀). Error in Cᵢ corrupts Pᵢ and Pᵢ₊₁. Sequential only.
CFB
Cipher Feedback		 Cᵢ = Pᵢ⊕E(K,Cᵢ₋₁) Pᵢ = Cᵢ⊕E(K,Cᵢ₋₁) Stream mode from block cipher. Self-synchronizing. <block-size operations possible.
OFB
Output Feedback		 Oᵢ=E(K,Oᵢ₋₁); Cᵢ=Pᵢ⊕Oᵢ Pᵢ=Cᵢ⊕Oᵢ Keystream pre-computable. Bit errors don't propagate. No feedback from ciphertext.
CTR
Counter		 Cᵢ=Pᵢ⊕E(K,Nonce∥i) Pᵢ=Cᵢ⊕E(K,Nonce∥i) Fully parallelizable. Random access decryption. Most modern (used in AES-GCM).
⚠️ ECB Penguin Problem
ECB encrypts identical plaintext blocks to identical ciphertext blocks, revealing structure (the famous ECB penguin). NEVER use ECB for real data. CBC and CTR are exam favorites.
RC4 — Stream Cipher

RC4 generates a pseudo-random keystream XORed with plaintext. Two phases: KSA (initialize 256-byte permutation S using key) and PRGA (generate keystream bytes). Used in old WEP/SSL. Deprecated (RFC 7465 prohibits in TLS).

KSA (Key Scheduling Algorithm)
Initialize: S[i] = i for i = 0..255
j = 0
for i = 0 to 255:
  j = (j + S[i] + Key[i mod keylen]) mod 256
  swap(S[i], S[j])
PRGA (Pseudo-Random Generation)
i = 0, j = 0
loop:
  i = (i + 1) mod 256
  j = (j + S[i]) mod 256
  swap(S[i], S[j])
  k = S[(S[i] + S[j]) mod 256] ← keystream byte
  output: plaintext_byte ⊕ k
IDEA — International Data Encryption Algorithm

Designed by Lai and Massey. Mixes three "incompatible" algebraic operations (no two distribute over each other) for strong security.

  • Block size: 64 bits (4 × 16-bit sub-blocks)
  • Key size: 128 bits → 52 sub-keys of 16 bits each
  • Rounds: 8 full rounds + 1 output transformation
  • Status: Patent expired (2012). Used in older PGP versions.
IDEA Three Operations
XOR: a ⊕ b (bitwise XOR)
Addition: a ⊞ b = (a + b) mod 2¹⁶
Multiply: a ⊙ b = (a × b) mod (2¹⁶ + 1) [0 treated as 2¹⁶]
No pair distributes over another → strong mixing

RSA Algorithm

RSA (Rivest–Shamir–Adleman, 1977) is the most widely used public-key system. Security relies on the integer factorization problem: given n = pq, infeasible to factor for large p, q.

Key Generation:

  1. Choose large distinct primes p and q
  2. Compute n = p × q (public modulus)
  3. Compute φ(n) = (p−1)(q−1) (kept secret)
  4. Choose e: 1 < e < φ(n), gcd(e, φ(n)) = 1 (common: e = 65537)
  5. Compute d = e⁻¹ mod φ(n) via Extended Euclidean
  6. Public key: (e, n) | Private key: (d, n). Delete p, q, φ(n).
RSA Operations
Encrypt (use receiver's public key): C = Mᵉ mod n
Decrypt (use own private key): M = Cᵈ mod n

Correctness: Mᵉᵈ ≡ M^(1+kφ(n)) ≡ M × (Mᶠ⁽ⁿ⁾)ᵏ ≡ M (mod n) by Euler's theorem
Security: minimum 2048-bit keys; 4096-bit recommended
✦ Full RSA Example — p=61, q=53
n = 61 × 53 = 3233
φ(3233) = (61−1)(53−1) = 60 × 52 = 3120
Choose e = 17 [gcd(17, 3120) = 1 ✓]
Find d: 17d ≡ 1 (mod 3120) → d = 2753
Verify: 17 × 2753 = 46801 = 15×3120 + 1 ✓
Public key: (17, 3233) | Private key: (2753, 3233)
Encrypt M=65: C = 65^17 mod 3233 = 2790
Decrypt: M = 2790^2753 mod 3233 = 65 ✓
RSA recovers M = 65 ✓
✦ Simpler Example — p=3, q=11
n = 33, φ(33) = 2×10 = 20
e = 7 [gcd(7,20)=1], d = 3 [7×3=21≡1 mod 20 ✓]
Encrypt M=2: C = 2^7 mod 33 = 128 mod 33 = 29
Decrypt C=29: M = 29^3 mod 33 = 24389 mod 33 = 2 ✓
Public(7,33), Private(3,33)
✦ RSA Fast Exponentiation — Compute 7^13 mod 33
13 in binary = 1101 → use bits 8,4,1
Squares: 7^1≡7, 7^2=49≡16, 7^4=16²=256≡25, 7^8=25²=625≡31 (mod 33)

Diffie-Hellman Key Exchange

DH (1976): allows two parties to establish a shared secret over a public channel with no prior communication. Security = Discrete Logarithm Problem.

Protocol:

  1. Public: large prime p and primitive root g
  2. Alice chooses secret a, sends A = gᵃ mod p
  3. Bob chooses secret b, sends B = gᵇ mod p
  4. Alice: K = Bᵃ mod p = g^(ab) mod p
  5. Bob: K = Aᵇ mod p = g^(ab) mod p

Eavesdropper sees p, g, A, B — cannot find K without solving DLP.

DH Summary
Public: p (prime), g (primitive root mod p)
Alice: a → A = gᵃ mod p
Bob: b → B = gᵇ mod p
Shared: K = Bᵃ mod p = Aᵇ mod p = g^(ab) mod p
Diffie-Hellman Exchange
✦ DH Numerical Example — p=23, g=5
Alice chooses secret a=6:
A = 5^6 mod 23: 5^2≡2, 5^3≡10, 5^6=(5^3)²=100 mod 23≡8
Bob chooses secret b=15:
B = 5^15 mod 23: 5^4≡5^2×5^2≡4, 5^8=4²≡16
5^15≡5^8×5^4×5^2×5^1≡16×4×2×5=640 mod 23≡19
Alice computes shared key:
K = B^a mod p = 19^6 mod 23
19^2=361≡16, 19^3=16×19=304≡5, 19^6=5²=25≡2 (mod 23)
Bob computes shared key:
K = A^b mod p = 8^15 mod 23
8^2=18, 8^4=2, 8^8=4, 8^15=4×2×18×8=1152≡2 (mod 23)
∴ Shared secret K = 2 (both sides agree ✓)
Man-in-the-Middle (MITM) Attack on DH

DH is vulnerable to MITM because it provides no authentication. An attacker Mallory intercepts and replaces exchanged values:

  1. Alice sends A = gᵃ to Bob; Mallory intercepts, sends her own A' = gᵐ to Bob
  2. Bob sends B = gᵇ to Alice; Mallory intercepts, sends her own B' = gᵐ' to Alice
  3. Alice computes K₁ = (gᵐ')ᵃ = g^(am') — shared with Mallory
  4. Bob computes K₂ = (gᵐ)ᵇ = g^(bm) — shared with Mallory
  5. Mallory decrypts Alice's messages with K₁, re-encrypts with K₂ to Bob

Prevention: Authenticated DH (certificates, PKI, digital signatures on the DH values).

⚠️ DH is Key Exchange Only — Not Encryption
DH only establishes a shared secret. It does NOT encrypt data directly. The shared secret is then used as a symmetric key (e.g., for AES). DH also provides no authentication by itself — always combine with certificates or signatures.
ElGamal Encryption

ElGamal (1985) is a public-key system based on DLP. Probabilistic — same plaintext encrypts to different ciphertexts each time (due to random k). Ciphertext is 2× size of plaintext.

Key Generation:

  1. Choose prime p, generator g of Z*_p
  2. Alice chooses secret a (private key), computes A = gᵃ mod p (public key)
  3. Public key: (p, g, A). Private key: a.
ElGamal Encrypt / Decrypt
Encrypt (Bob to Alice): choose random k
  C₁ = gᵏ mod p
  C₂ = M × Aᵏ mod p
  Ciphertext: (C₁, C₂)

Decrypt (Alice with private a):
  K = C₁ᵃ mod p (= gᵃᵏ mod p)
  M = C₂ × K⁻¹ mod p
✦ ElGamal Example — p=23, g=5, a=6
Public: A = 5^6 mod 23 = 8 | Private: a = 6
Bob encrypts M=10 with random k=3:
C₁ = g^k mod p = 5^3 mod 23 = 125 mod 23 = 10
C₂ = M × A^k mod p = 10 × 8^3 mod 23
8^3 = 512, 512 mod 23 = 512 − 22×23 = 6
C₂ = 10 × 6 mod 23 = 60 mod 23 = 14
Ciphertext: (C₁, C₂) = (10, 14)
Alice decrypts:
K = C₁^a mod p = 10^6 mod 23
10^2=100≡8, 10^3=8×10=80≡11, 10^6=11²=121≡6 (mod 23)
K⁻¹ mod 23: 6×4=24≡1 → K⁻¹ = 4
M = C₂ × K⁻¹ mod p = 14 × 4 = 56 mod 23 = 10
∴ M = 10 recovered ✓ (ElGamal decryption works)
Elliptic Curve Cryptography (ECC)

ECC provides equivalent security to RSA with much smaller keys. A 256-bit ECC key ≈ 3072-bit RSA key in security. Based on the Elliptic Curve Discrete Logarithm Problem (ECDLP).

Elliptic Curve: y² = x³ + ax + b (mod p), with 4a³ + 27b² ≠ 0.

Group Operation (Point Addition):

  • P + Q = R: draw line through P and Q, find intersection with curve, reflect over x-axis
  • P + P = 2P (point doubling): tangent to curve at P
  • P + O = P (O is the point at infinity, identity element)

ECDH: Same as DH but scalar multiplication over elliptic curve instead of modular exponentiation. Alice: A = a·G, Bob: B = b·G, Shared = a·B = b·A = ab·G.

Advantages: Smaller keys, faster computation, less power — ideal for IoT/mobile.

ECC Key Sizes vs RSA (comparable security)
ECC 160-bit ≈ RSA 1024-bit
ECC 224-bit ≈ RSA 2048-bit
ECC 256-bit ≈ RSA 3072-bit
ECC 384-bit ≈ RSA 7680-bit
ECDLP: given P and Q=kP, find k — computationally hard

Hash Function Requirements

A cryptographic hash function H maps variable-length input M to fixed-length output h = H(M).

Six Properties (in increasing security order):

  1. Variable input length: Can take any length input
  2. Fixed output length: Always produces same-length hash
  3. Efficiency: Easy to compute H(M) for any M
  4. Pre-image resistance (one-wayness): Given h, infeasible to find M such that H(M) = h
  5. Second pre-image resistance (weak collision resistance): Given M, infeasible to find M' ≠ M with H(M') = H(M)
  6. Collision resistance (strong): Infeasible to find any (M, M') pair with H(M) = H(M')

Avalanche effect: Small change in input → large, unpredictable change in hash (≈50% of bits flip).

Security Levels (brute force)
Pre-image attack: 2ⁿ operations (n = hash bits)
Second pre-image: 2ⁿ operations
Collision attack (Birthday): 2^(n/2) operations
e.g., SHA-256 (256-bit): collision ≈ 2¹²⁸ ops → secure
MD5 — Message Digest 5

MD5 (Rivest, 1991): produces 128-bit hash. Uses Merkle-Damgård construction with four rounds of 16 operations each = 64 total operations. Padding: message padded to 448 mod 512 bits, then 64-bit length appended → multiple of 512.

State: Four 32-bit registers (A, B, C, D) initialized with constants.

Round functions:

  • Round 1: F(B,C,D) = (B∧C) ∨ (¬B∧D)
  • Round 2: G(B,C,D) = (B∧D) ∨ (C∧¬D)
  • Round 3: H(B,C,D) = B ⊕ C ⊕ D
  • Round 4: I(B,C,D) = C ⊕ (B ∨ ¬D)

Status: Cryptographically broken — collision attacks demonstrated in practice. Do not use for security. Only for checksums/non-security integrity.

MD5 Parameters
Output: 128 bits (32 hex chars)
Block size: 512 bits
Rounds: 4 × 16 = 64 steps
State: A, B, C, D (each 32 bits)
BROKEN: Collisions found in seconds on modern hardware
SHA-512

SHA-512 (FIPS 180-4): part of SHA-2 family. Uses Merkle-Damgård with Davies-Meyer compression. Eight 64-bit state variables (a–h). Each round uses two non-linear functions (Σ, σ) plus majority and choice functions.

Padding: Append '1' bit, then zeros, until message ≡ 896 (mod 1024), then append 128-bit length. Block size = 1024 bits.

SHA Family Comparison:

SHA-224 224 bits 512 bits 64 32-bit Truncated SHA-256
SHA-256 256 bits 512 bits 64 32-bit Secure
SHA-384 384 bits 1024 bits 80 64-bit Secure
SHA-512 512 bits 1024 bits 80 64-bit Secure

Ch(e,f,g) = (e∧f) ⊕ (¬e∧g) ← Choice

Σ₀(a) = ROTR²⁸(a) ⊕ ROTR³⁴(a) ⊕ ROTR³⁹(a)

T₂ = Σ₀(a) + Maj(a,b,c)
New a = T₁ + T₂; New e = d + T₁
HMAC — Hash-based Message Authentication Code

HMAC combines a hash function with a secret key to provide both integrity and authentication. Resists length extension attacks (unlike naive hash-key concatenation).

Two padded keys: ipad = 0x36 repeated, opad = 0x5C repeated (both XORed with key, padded to block size).

HMAC Formula
ipad = 0x3636...36 (block-length, e.g. 64 bytes for SHA-256)
opad = 0x5C5C...5C (block-length)
HMAC(K, M) = H((K ⊕ opad) ∥ H((K ⊕ ipad) ∥ M))

Inner hash: H(K⊕ipad ∥ M)
Outer hash: H(K⊕opad ∥ inner_hash)
Security: 2^(n/2) to find collision (birthday), 2ⁿ to forge

HMAC vs MAC: MAC uses a block cipher (e.g., CBC-MAC). HMAC uses a hash function. HMAC is faster in software. Both provide authentication and integrity but NOT confidentiality.

Birthday Attack

Based on the Birthday Paradox: in a group of just 23 people, probability that two share a birthday > 50%. Applied to hashing: finding any collision (not a specific one) takes only ~2^(n/2) attempts for n-bit hash.

Attack: Generate 2^(n/2) random messages and their hashes. By birthday paradox, with high probability, two will collide. This is much less than 2ⁿ (brute force).

Defense: Use long enough hash (SHA-256 gives 2¹²⁸ collision resistance, SHA-512 gives 2²⁵⁶).

Birthday Attack Complexity
For n-bit hash function H:
Brute-force pre-image: 2ⁿ operations
Birthday collision attack: ≈ 2^(n/2) operations

Example: 64-bit hash → 2³² ≈ 4 billion operations to find collision
128-bit MD5 → 2⁶⁴ ≈ feasible with modern hardware (BROKEN)
256-bit SHA-256 → 2¹²⁸ → secure against birthday attacks

Message Authentication Code (MAC)

MAC provides integrity + authentication (not confidentiality). Computed using a shared secret key K and message M. Both sender and receiver share K; only they can generate/verify MACs.

DAA (Data Authentication Algorithm): Based on DES-CBC. Final 16 or 32-bit CBC output is the MAC.

MAC vs Digital Signature: MAC uses symmetric key (both parties must share key); DS uses asymmetric key (private to sign, public to verify — supports non-repudiation).

MAC Concept
MAC = C(K, M) where K = shared secret key
Sender: transmit (M, MAC) | Receiver: compute MAC', compare with MAC
Security: attacker without K cannot forge valid MAC
CBC-MAC: process M through DES-CBC, output last block (or part of it)
RSA Digital Signature

Digital signatures provide: Authentication (who signed), Integrity (not modified), Non-repudiation (signer can't deny). RSA signatures reverse the RSA key usage: sign with private key, verify with public key.

Note on efficiency: In practice, only the hash of the message is signed (not the full message), since RSA is slow.

RSA Signature Scheme
Sign (Alice, private key d): S = H(M)ᵈ mod n
Verify (anyone, public key e): H(M) == Sᵉ mod n?

Full message version (small M):
Sign: S = Mᵈ mod n
Verify: M == Sᵉ mod n
✦ RSA Digital Signature Example
Alice's keys: p=11, q=13, n=143, φ(n)=10×12=120
e=7, d=103 (7×103=721=6×120+1 ✓)
Message M=9
Sign: S = M^d mod n = 9^103 mod 143
9^2≡81, 9^4≡126, 9^8≡3, 9^16≡9, 9^32≡81, 9^64≡126 (mod 143)
103=64+32+4+2+1: S = 126×81×126×81×9 mod 143
126×81≡53, 53×126≡100, 100×81≡92, 92×9≡113 (all mod 143)
∴ S = 113
Verify: S^e mod n = 113^7 mod 143
113^2≡42, 113^4≡48, 113^7≡48×42×113 (mod 143)
48×42≡14, 14×113≡9 (mod 143)
∴ 113^7 mod 143 = 9 = M ✓ Signature verified!
ElGamal Digital Signature

ElGamal DS uses randomness — each signature is unique even for the same message. Private key = a, public key = (p, g, A = gᵃ mod p). Requires a random k (secret, unique per signature). Critical: never reuse k!

ElGamal Signature
Sign (private key a, random k where gcd(k, p−1)=1):
  r = gᵏ mod p
  s = k⁻¹(H(M) − a·r) mod (p−1)
  Signature: (r, s)

Verify (public key A = gᵃ mod p):
  v₁ = g^H(M) mod p
  v₂ = Aʳ · rˢ mod p
  Signature valid if v₁ == v₂
⚠️ ElGamal DS — Never Reuse k!
If the same k is used for two different messages, the private key a can be recovered. This was the vulnerability exploited in the Sony PS3 hack (they used constant k in ECDSA).
DSS / DSA — Digital Signature Standard

DSS (FIPS 186) uses DSA algorithm. Similar to ElGamal but more efficient — designed specifically for signatures (can't encrypt). Uses a 160-bit subgroup order q within a larger prime p.

Parameters: p (1024-bit prime), q (160-bit prime, q | p−1), g (generator of order q), x (private, 0 < x < q), y = gˣ mod p (public)

DSA Sign / Verify
Sign (private x, random k, 0<k<q):
  r = (gᵏ mod p) mod q
  s = k⁻¹(H(M) + x·r) mod q
  Signature: (r, s)

Verify (public y):
  w = s⁻¹ mod q
  u₁ = H(M)·w mod q
  u₂ = r·w mod q
  v = (g^u₁ · y^u₂ mod p) mod q
  Valid if v == r
Kerberos Authentication

Kerberos is a trusted third-party authentication protocol using symmetric cryptography. Provides single sign-on (SSO). Based on Needham-Schroeder protocol.

Components: Client (C), Authentication Server (AS), Ticket-Granting Server (TGS), Service Server (SS)

Protocol Flow:

  1. C → AS: "I want a TGT" (plaintext, no password sent)
  2. AS → C: TGT (encrypted with TGS key K_TGS) + Session key K_C,TGS (encrypted with C's key K_C)
  3. C → TGS: TGT + Authenticator (encrypted with K_C,TGS) + Service request
  4. TGS → C: Service ticket (encrypted with SS key) + Session key K_C,SS
  5. C → SS: Service ticket + Authenticator
  6. SS → C: Confirmation (optional mutual authentication)

Limitations: Single point of failure (KDC), Kerberos server must always be online, vulnerable to password guessing if weak passwords, timestamps needed (clock skew max 5 min).

Kerberos Key Concepts
TGT (Ticket Granting Ticket): long-term credential, from AS, valid hours/day
Service Ticket: short-term, one-per-service
Authenticator: timestamp encrypted with session key → prevents replay attacks
Kerberos uses timestamps (not nonces) to prevent replay attacks
All tickets include: client ID, client network addr, validity period, session key
Kerberos Authentication Flow
X.509 Certificates

X.509 is the standard for public-key certificates. A certificate binds a public key to an identity, signed by a Certificate Authority (CA).

X.509 Certificate Fields (v3):

  • Version (v1/v2/v3)
  • Serial Number (unique per CA)
  • Signature Algorithm (e.g., SHA256withRSA)
  • Issuer (CA's distinguished name)
  • Validity Period (not before, not after)
  • Subject (owner's distinguished name)
  • Subject Public Key Info (algorithm + public key)
  • Extensions (v3 only: key usage, SAN, etc.)
  • CA's Digital Signature

Certificate verification: Verify CA's signature on the cert using CA's public key. Chain of trust ends at a root CA (self-signed).

Certificate Chain of Trust
Root CA (self-signed) → Intermediate CA → End-entity cert
Each cert is signed by the issuer's private key
Verification: check each cert's signature using issuer's public key
CRL (Certificate Revocation List): list of revoked certs
OCSP (Online Certificate Status Protocol): real-time revocation check
PKI — Public Key Infrastructure

PKI is the framework for managing digital certificates and public-key encryption. Enables secure communication at scale.

Components:

  • CA (Certificate Authority): Issues and signs certificates. Root CA is the trust anchor.
  • RA (Registration Authority): Verifies applicants before CA issues cert.
  • Certificate Repository: Stores/distributes certificates (LDAP, web).
  • CRL/OCSP: Certificate revocation mechanisms.
  • End Entities: Users/servers that own certificates.

Web of Trust (PGP model): Alternative to hierarchical PKI. Users sign each other's keys. No central CA — trust built through network of signatures.

PKI Hierarchy vs Web of Trust
Hierarchical PKI: Root CA → Intermediate CA → End cert
  Centralized, scalable, used in TLS/HTTPS
Web of Trust: users sign each other's public keys (PGP model)
  Decentralized, used in email (PGP/GPG)

TLS Handshake Protocol

TLS (Transport Layer Security) provides confidentiality, integrity, and authentication at the transport layer. The handshake establishes session parameters and shared keys before any application data is sent.

TLS 1.3 Handshake (simplified):

  1. ClientHello: TLS version, supported cipher suites, client random, key share (ECDHE)
  2. ServerHello: Chosen cipher suite, server random, key share, certificate, CertificateVerify, Finished
  3. Client: Verifies server cert, computes master secret, sends Finished
  4. Application data flows encrypted

TLS 1.2 Handshake (exam-common version):

  1. ClientHello (version, random, cipher suites)
  2. ServerHello + Certificate + ServerHelloDone
  3. ClientKeyExchange (pre-master secret, encrypted with server's public key)
  4. Both sides derive Master Secret → Session Keys
  5. ChangeCipherSpec + Finished (both sides)
TLS 1.2 Handshake Sequence
Master Secret Derivation (TLS 1.2)
pre_master_secret: 48-byte value (RSA: encrypted; DHE: DH result)
master_secret = PRF(pre_master_secret, "master secret", rand_C ∥ rand_S)
Session keys derived: client_write_key, server_write_key, IVs, MACs
PRF = HMAC-SHA256 (in TLS 1.2)

IPSec Architecture

IPSec provides security at the IP layer (Layer 3). Protects all traffic transparently to applications. Used in VPNs.

Two Protocols: AH (Authentication Header) for integrity/auth only, and ESP (Encapsulating Security Payload) for confidentiality + integrity.

Two Modes:

  • Transport Mode: Protects IP payload only. Original IP header preserved. Used between end hosts.
  • Tunnel Mode: Entire original IP packet encapsulated. New IP header added. Used for VPNs (gateway-to-gateway).

SA (Security Association): Unidirectional relationship defining security parameters (algorithm, key, lifetime). Identified by (SPI, destination IP, protocol). For bidirectional comms, need 2 SAs.

IKE (Internet Key Exchange): Protocol to establish SAs automatically. IKEv2 is current standard.

IPSec Modes
Transport: [IP hdr | AH/ESP | TCP/UDP | Data]
Tunnel: [New IP hdr | AH/ESP | Original IP hdr | TCP/UDP | Data]

SA identified by: (SPI, Dest IP, Protocol=AH or ESP)
SAD: Security Association Database (stores all active SAs)
SPD: Security Policy Database (what traffic needs IPSec)
ESP & AH Headers

AH (Authentication Header): Provides integrity and authentication of IP packet (including IP header for transport mode). Does NOT encrypt. Protocol number = 51.

ESP (Encapsulating Security Payload): Provides confidentiality (encryption), integrity, and authentication of IP payload. Encrypts the payload. Can optionally authenticate. Protocol number = 50. More commonly used than AH.

PGP — Pretty Good Privacy

PGP (Phil Zimmermann, 1991) provides email security: confidentiality, authentication, compression, and radix-64 conversion (for email compatibility). Uses a Web of Trust for key distribution (no central CA).

PGP Services:

  • Authentication: SHA-1 hash of message → signed with sender's RSA/DSS private key
  • Confidentiality: Message encrypted with one-time symmetric key (IDEA/3DES/AES) → key encrypted with recipient's RSA public key
  • Compression: ZIP after signing, before encrypting (better compression; also hides patterns)
  • Email compatibility: Radix-64 (Base64) conversion of binary data to printable ASCII
  • Segmentation: Large messages split into email-size segments
PGP Send Process (Auth + Confidentiality)
1. Hash: h = SHA(M)
2. Sign: sig = RSA(h, K_priv_sender) ← sender's private key
3. Concatenate: M ∥ sig
4. Compress: Z(M ∥ sig)
5. Generate one-time symmetric key K_s
6. Encrypt message: E(K_s, compressed_data)
7. Encrypt key: E(K_pub_receiver, K_s) ← receiver's public key
8. Transmit: encrypted_key ∥ encrypted_data (radix-64)
PGP Receive Process
1. Decode radix-64
2. Decrypt symmetric key: K_s = RSA_decrypt(encrypted_key, K_priv_receiver)
3. Decrypt message: D(K_s, encrypted_data) → compressed
4. Decompress → M ∥ sig
5. Verify: compare H(M) with RSA(sig, K_pub_sender)

S/MIME — Secure/Multipurpose Internet Mail Extensions

S/MIME is the standard email security protocol for corporate environments. Uses X.509 certificates (unlike PGP's Web of Trust). Built into most email clients (Outlook, Apple Mail).

Services provided:

  • Signed data: Clear-signed message with digital signature
  • Clear-signed data: Signature only, message readable without S/MIME
  • Signed & enveloped: Both encryption and signing

Firewalls

A firewall controls network traffic between zones based on rules (policy). The first line of network defense.

Types:

  • Packet-Filtering Firewall: Examines each packet in isolation (IP src/dst, ports, protocol). Stateless. Fast but limited. Cannot detect fragmentation attacks or stateful attacks.
  • Stateful Inspection (Dynamic Packet Filtering): Tracks connection state table. Knows if packet is part of established connection. Better protection than simple packet filtering.
  • Application-Layer (Proxy) Firewall: Understands application protocols (HTTP, FTP, DNS). Can filter by content, URL, commands. Slower but most secure.
  • Circuit-Level Gateway: Works at session layer. Validates TCP handshake. Doesn't inspect content. (e.g., SOCKS proxy)
  • Next-Generation Firewall (NGFW): Combines all above + IDS/IPS, deep packet inspection, application awareness.

DMZ (Demilitarized Zone): A network segment between the external firewall and internal network where public-facing servers (web, mail, DNS) reside.

Default policies: Default-deny (whitelist) is more secure than default-allow (blacklist).

Firewall Types Summary
Packet Filter: L3/L4 — IP/Port rules — stateless — fastest
Stateful Inspection: L3/L4 — tracks connections — standard
Application Proxy: L7 — protocol-aware — content filter — slowest
NGFW: L3–L7 + DPI + IPS + App-ID — current standard
DMZ: External FW → DMZ (public servers) → Internal FW → LAN
Intrusion Detection Systems (IDS)

IDS monitors network/system for malicious activity. Detects but does NOT block (that's IPS — Intrusion Prevention System).

Types by deployment:

  • NIDS (Network-based): Monitors network traffic at strategic points
  • HIDS (Host-based): Monitors a single host (logs, file integrity, processes)

Detection Methods:

  • Signature-based (Misuse detection): Matches traffic against known attack patterns (signatures). Low false positives, but can't detect zero-days.
  • Anomaly-based (Statistical): Builds baseline of normal behavior; alerts on deviations. Can detect novel attacks but higher false positive rate.
  • Stateful Protocol Analysis: Compares observed protocol behavior against predefined profiles of normal protocol use.

Metrics: True Positive (TP), False Positive (FP = false alarm), True Negative (TN), False Negative (FN = missed attack).

IDS vs IPS
IDS: detect only → alert → analyst investigates
IPS: detect + block → inline device → automatic response

Signature-based: low FP, misses zero-days
Anomaly-based: detects novel, higher FP
Honeypot: decoy system to attract attackers (detect + study)
SET — Secure Electronic Transaction

SET was developed by Visa and Mastercard (1997) for secure credit card transactions over the internet. Uses digital certificates for all parties: cardholder, merchant, payment gateway.

Participants: Cardholder, Merchant, Payment Gateway (bank), CA (certificate authority), Issuer (cardholder's bank), Acquirer (merchant's bank)

Key feature — Dual Signature: The merchant sees the order info but NOT the credit card number. The bank sees the credit card info but NOT the order details. Yet both can verify the link between them.

Dual Signature mechanism:

  1. Cardholder creates Order Info (OI) and Payment Info (PI)
  2. H(OI) and H(PI) computed
  3. POMD = H(H(PI) ∥ H(OI))
  4. DS = E(K_priv_cardholder, POMD) — dual signature
  5. Merchant gets: OI, H(PI), DS — can verify OI linked to PI without seeing PI
  6. Bank gets: PI, H(OI), DS — can verify PI linked to OI without seeing OI
SET Dual Signature
POMD = H(H(PI) ∥ H(OI))
DS = Sign(K_priv_cardholder, POMD)

Merchant verifies: H(H(PI_received) ∥ H(OI)) == Verify(DS)
Bank verifies: H(H(PI) ∥ H(OI_received)) == Verify(DS)
Neither party sees the other's data — privacy preserved!
