  • Minimum confirmation requirement: For driver payout, platform requires ≥3 block confirmations → reduces risk of chain reorganization reversing the payment.

3. Two Points of Delay — Detailed Analysis

⚠ DELAY POINT 1 — Mempool Congestion (Step ④)

Why it occurs: During high network activity (NFT drops, DeFi events, market volatility), thousands of transactions flood the mempool simultaneously. The block size limits how many transactions can be included per block. Transactions are sorted by gas price (fee per unit of computation). A withdrawal with standard/low gas price gets pushed to the back of the queue behind higher-paying transactions.

Example: During Ethereum's peak in 2021, mempool held 150,000+ pending transactions and gas prices spiked to 1000+ Gwei. A low-fee transaction could wait 30–60 minutes or be dropped after 72 hours.

⚠ DELAY POINT 2 — Mining / Block Production Variability (Step ⑥)

Why it occurs: PoW block time is probabilistic — blocks are found via a Poisson process. Bitcoin targets 10-minute block intervals but actual times follow an exponential distribution. A block can take 30 seconds or 45 minutes depending on luck. Additionally, after a difficulty adjustment period, if many miners leave the network simultaneously, difficulty remains high → blocks take much longer than 10 minutes until the next adjustment (2016 blocks = ~2 weeks).

Orphan blocks: Two miners solve a block simultaneously → chain fork → one block eventually orphaned → transactions in orphaned block return to mempool → re-confirmation needed.

Fix: Exchanges use dynamic confirmation thresholds — for smaller amounts, 3 confirmations; for large withdrawals, 6+ confirmations. Real-time monitoring of block propagation and chain reorganization depth is essential.

1. Decentralization

Definition: In a traditional (centralized) system, a single entity (bank, government, server) holds and controls all data. In blockchain, there is no central authority. The ledger is maintained collectively by thousands of peer-to-peer nodes spread across the globe. Each node maintains its own copy of the full blockchain. To add a new block, a consensus of the majority of nodes is required — no single node can unilaterally alter the ledger.

❌ Centralized

  • Admin can alter/delete records
  • Requires trust in one party
✓ Decentralized (Blockchain)

  • Majority needed to change anything
  • Trustless — trust the math

2. Transparency

Definition: On a public blockchain (Bitcoin, Ethereum), every transaction ever made is permanently visible to any participant or observer via a block explorer. Transaction data (sender address, receiver address, amount, timestamp) is open for inspection. Nuance: Transparency means transaction data is public, but identities are pseudonymous — linked to wallet addresses (public keys), not real names.

3. Immutability

Definition: Once a transaction is included in a confirmed block and buried under subsequent blocks, it becomes practically impossible to alter or delete. Q1b. What is a cryptographic hash function? Mention any three properties of a cryptographically secure hash function. 5 Marks Module 1 | CO1 | BL2

Answer — Cryptographic Hash Functions

Definition

A cryptographic hash function is a mathematical algorithm that takes an input (message) of arbitrary length and produces a fixed-size output called a hash digest (fingerprint). It is a one-way function — easy to compute forward, computationally infeasible to reverse.

Input: "Hello, Blockchain" → SHA-256 → a8f5f167f44f4964e6c998dee827110c... (256 bits / 64 hex chars) Input: "Hello, Blockchain!" → SHA-256 → 9f86d081884c7d659a2feaa0c55ad015... (completely different!)

Three Key Properties

# Property Meaning Blockchain Relevance
1 Pre-image Resistance (One-Way) Given hash output H, computationally infeasible to find input M such that hash(M)=H. Miners cannot work backwards from target hash — must brute-force forward.
2 Collision Resistance Computationally infeasible to find two distinct inputs M1 ≠ M2 such that hash(M1)=hash(M2). No two different blocks can have same hash → prevents block substitution fraud.
3 Avalanche Effect A tiny change in input (even 1 bit) causes ~50% of output bits to change. Any modification to block data produces completely different hash → immediately detectable.

Additional Properties: Deterministic, Second pre-image resistance, Fixed output size (SHA-256 always 256 bits), Efficiency (milliseconds to compute).

📝 Exam Tip: Bitcoin uses SHA-256 (double SHA-256 for block hashing); Ethereum uses Keccak-256 (SHA-3 variant). Always connect each property to a real blockchain use case for full marks.

Q2. An attacker tries to modify a transaction recorded three blocks earlier in a blockchain. Explain why altering one block breaks the entire blockchain structure using the concept of cryptographic hashes and block linking. 10 Marks Module 1 | CO2 | BL3

Answer — Why Altering One Block Breaks the Entire Chain

1. Block Linking Mechanism

Each block contains a Previous Block Hash in its header — the SHA-256 hash of the preceding block's header. This creates a cryptographic chain: Block N's existence depends on Block N-1's exact content, which depends on Block N-2's, back to Genesis.

2. The Attack Scenario — Step by Step

Chain: B0 (Genesis) → B1 → B2 → B3 → B4 → B5 (current tip). Attacker modifies a transaction in B2.

1
Attacker modifies transaction in B2. Changes Alice→Bob: 5 BTC to 0.1 BTC. The Merkle Root of B2 changes → H(B2) completely changes (SHA-256 avalanche effect).
2
B3's Prev_Hash now points to a ghost. B3 was created with Prev_Hash = old H(B2). After modification, new H(B2) is completely different → B3 is now invalid. Every full node independently checks → mismatch detected instantly.
3
Cascade: B4 and B5 also become invalid. Since B3 is invalid, H(B3) is wrong → B4's Prev_Hash invalid → B5 invalid. Every block after the tampered block becomes invalid.
4
Attacker must re-mine ALL subsequent blocks. Must resolve PoW for B2', B3', B4', B5' — ~10 min each. Meanwhile honest network adds B6, B7, B8... Attacker falls further behind unless >50% hash power.

3. Diagram — Tamper Cascade

5. Merkle Root — Intra-Block Integrity

Within each block, the Merkle Root is the root hash of all transactions. Modifying one transaction changes its leaf hash → all parent hashes up to Merkle Root → block header → block hash → next block's Prev_Hash. This two-layer system ensures any modification at any granularity is detectable.

Q3a. What is secret sharing? Explain the concept of a (K, N) threshold scheme. 5 Marks Module 2 | CO1 | BL2

Answer — Secret Sharing and (K, N) Threshold Scheme

1. What is Secret Sharing?

Secret sharing is a cryptographic technique for distributing a secret (e.g., a private key) among a group of N participants, such that: no single participant alone can reconstruct the secret; only when K or more participants combine their shares can the secret be recovered; any subset fewer than K reveals nothing about the secret (information-theoretic security).

2. The (K, N) Threshold Scheme — Shamir's Secret Sharing

  • N = total participants each receiving one share.
  • K = minimum shares required to reconstruct the secret (K ≤ N).
  • Any group of K or more → can recover secret. Fewer than K → learns absolutely nothing.

3. Mathematical Basis — Polynomial Interpolation (Shamir, 1979)

f(x) = S + a1*x + a2*x^2 + ... + a_{K-1}*x^{K-1} (mod prime p) Where: S = secret (constant term); ai = random coefficients; p = large prime Shares: each participant i receives (i, f(i)) Recovery: Any K points uniquely determine degree-(K-1) polynomial via Lagrange interpolation → f(0) = S

4. Example — (3, 5) Scheme

Parameter Value
N (total shares) 5 executives hold shares
K (threshold) 3 — any 3 can recover the key
Polynomial degree K-1 = 2 (quadratic)
Security guarantee Any 2 shares reveal ZERO information about S
Fault tolerance Up to 2 participants can lose shares or be unavailable
📝 Exam Tip: Key phrase: "A (K,N) threshold scheme uses a degree-(K-1) polynomial over a finite field. Secret S = f(0). K points uniquely determine the polynomial via Lagrange interpolation; fewer than K points reveal nothing — information-theoretically secure."

Q3b. Define double spending. Why is it considered a major problem in digital currencies? 5 Marks Module 2 | CO1 | BL2

Answer — Double Spending in Digital Currencies

1. Definition

Double spending is an attack where the same unit of digital currency (same UTXO/coin) is fraudulently spent more than once. The attacker broadcasts two conflicting transactions simultaneously — attempting to pay two different recipients with the same funds.

2. Why It's Unique to Digital Currencies

Physical cash cannot be double-spent — handing a note means you no longer hold it. But digital data is perfectly copyable. Without controls, Alice could send the same "coin file" to two shops simultaneously.

3. Types of Double-Spend Attacks

Attack Method Difficulty
Race Attack Broadcast two conflicting Txns simultaneously; merchant accepts 0-confirmation Tx Low — no mining power needed
Finney Attack Miner pre-mines block with double-spend, broadcasts after merchant accepts 0-conf payment Medium — requires miner capability
51% Attack Control >50% hash power → mine alternate chain with double-spend → release longer chain Very High

4. Why It's a Major Problem

  • Destroys trust: If coins can be copied and spent multiple times, they have no reliable value.
  • Undermines scarcity: A currency's value depends on scarcity. Double spending enables infinite money creation from nothing.
  • Centralization required (pre-blockchain): PayPal, Visa prevent double-spending via centralized database — the very centralization blockchain eliminates.
  • Bitcoin's core innovation: Satoshi's 2008 whitepaper specifically solved double-spending without a trusted third party via PoW + longest chain rule.

5. How Blockchain Prevents Double Spending

Q5. A blockchain block contains thousands of transactions. Explain how the Merkle tree helps verify whether a single transaction belongs to the block. 10 Marks Module 3 | CO3 | BL3

Answer — Merkle Tree and Transaction Verification

1. What is a Merkle Tree?

A Merkle tree (Ralph Merkle, 1979) is a binary hash tree where: Leaf nodes = SHA-256 hash of each transaction (H(Tx)); Internal nodes = H(left_child || right_child); Merkle Root = single root node — 32-byte fingerprint of ALL transactions. The Merkle Root is stored in the block header, protected by PoW.

2. Merkle Tree Structure

MERKLE ROOT (H_ABCD) ← stored in block header = H(H_AB || H_CD) / \ H_AB = H(H_A||H_B) H_CD = H(H_C||H_D) / \ / \ H_A=H(TxA) H_B=H(TxB) H_C=H(TxC) H_D=H(TxD) TxA TxB TxC TxD

3. Merkle Proof — Verifying a Single Transaction

To prove TxC belongs to this block, a full node provides a Merkle proof (authentication path):

1
Verifier computes: H_C = SHA-256(TxC)
2
Full node provides H_D (sibling). Verifier: H_CD = SHA-256(H_C || H_D)
3
Full node provides H_AB (sibling). Verifier: H_ABCD = SHA-256(H_AB || H_CD)
4
Compare computed H_ABCD with Merkle Root in block header. If equal → TxC verified! If mismatch → TxC NOT in this block.

4. Efficiency — Why Merkle Proof is Powerful

Method Data Needed For N Transactions
Naive: Download all transactions Entire block (megabytes) O(N) data
Merkle Proof Only sibling hashes on path to root O(log2 N) hashes

Example: Block with 4096 transactions requires only log2(4096) = 12 hashes (384 bytes) to verify any single transaction — vs 1 MB entire block.

5. SPV (Simplified Payment Verification)

SPV clients (mobile wallets) download only block headers (~80 bytes each). To verify a transaction: request Merkle proof from full node → verify against Merkle Root in trusted block header. Mobile wallets verify transactions with kilobytes instead of gigabytes.

Q1b. A mining pool operator notices that one miner produces many "near-valid" hashes with many leading zeros but rarely finds a full valid block. How can these near-valid hashes be used to estimate the miner's contribution to the pool? 5 Marks Module 3 | CO2 | BL2

Answer — Near-Valid Hashes (Shares) and Pool Contribution Estimation

1. What are "Near-Valid" (Share) Hashes?

A share (near-valid hash) is a hash meeting a lower difficulty target than the actual network difficulty — enough leading zeros to be significant but not enough to qualify as a valid block.

Network target (Bitcoin 2025): 77 leading zero bits → P_block ~1 in 10^23 Pool share target (lower): 40 leading zero bits → P_share ~1 in 10^12 A 10 TH/s miner produces: ~1 share per second (at 40-bit difficulty) ~1 valid block per century (at 77-bit difficulty) if mining solo

2. How Shares Estimate Hash Rate

Hash rate estimate: Hash rate ≈ Shares_per_second × 2^share_difficulty Example: Miner submits 3600 shares/hour at 40-bit difficulty: Hash rate = (3600/3600) × 2^40 = 2^40 ≈ 1.1 TH/s

3. Proportional Reward Distribution

Miner Shares Share % Reward (if block = 3.125 BTC)
Our Miner 180,000 60% 1.875 BTC
Miner B 60,000 20% 0.625 BTC
Miner C 60,000 20% 0.625 BTC

4. Pool Reward Methods

Method How Shares Used
PPS (Pay Per Share) Fixed amount per valid share; pool bears variance risk
PROP (Proportional) When block found: each miner gets shares/total_shares × reward
PPLNS Only last N shares count; penalizes pool-hopping

5. Why Near-Valid Hashes Prove Real Work

A near-valid hash cannot be faked — requires same SHA-256 computation as valid hash. Hash function is uniformly distributed — miner can only produce near-valid hashes at their actual hardware rate. Submitting fake shares is impossible (would require hash preimage forgery). Shares are unforgeable proof of computational work proportional to actual hash rate.

Answer — Consensus Mechanisms and Proof of Work

1. Role of Consensus in Blockchain

Consensus is the mechanism by which all nodes in a decentralized, trustless network agree on the single canonical state of the distributed ledger — without requiring a central authority. It solves the fundamental problem of distributed agreement among mutually distrusting parties (the Byzantine Generals Problem).

Consensus Role Problem Solved How
Canonical Chain Selection Multiple valid blocks broadcast simultaneously → which one to accept? Longest chain rule (most accumulated PoW) / heaviest chain (PoS)
Double-Spend Prevention Alice sends same Bitcoin to Bob and Charlie simultaneously Only one branch of the fork survives → only one spend confirmed
Byzantine Fault Tolerance Some nodes are malicious or offline PoW requires majority honest hash power; PoS requires honest stake majority
Decentralized Decision Making Who decides which transactions are valid? All nodes independently verify using same consensus rules → emergent agreement
Sybil Resistance Attacker creates millions of fake identities to dominate voting PoW: voting power = computational work (costly); PoS: voting power = staked value (costly)
Finality When is a transaction truly irreversible? PoW: probabilistic finality after N confirmations; PoS (Casper): deterministic finality

2. Key Characteristics of Proof of Work (PoW)

# Characteristic Description
1 Computational Puzzle Miners must find a nonce value such that SHA-256(SHA-256(block header + nonce)) produces a hash with N leading zeros (where N = current difficulty). This puzzle is hard to solve but trivial to verify.
2 Asymmetric Effort Solving the puzzle requires enormous computation; verifying the solution requires a single hash computation. This asymmetry is what makes PoW secure — attackers must redo all the work.
3 Difficulty Adjustment Bitcoin adjusts difficulty every 2016 blocks (~2 weeks) to maintain a ~10-minute average block time. If blocks arrive faster than 10 min → difficulty increases; slower → decreases.
4 Probabilistic Finality Transactions are never 100% final, but probability of reversal decreases exponentially with each additional block confirmation. After 6 confirmations, reversal probability is negligible.
5 Energy Intensive Requires massive electricity and specialized hardware (ASICs). Bitcoin consumes ~120–150 TWh/year globally — comparable to some small countries.
6 Nakamoto Consensus (Longest Chain Rule) In case of fork, the valid chain with the most accumulated computational work (not simply the most blocks) is considered canonical.
7 51% Attack Threshold An attacker needs >50% of total network hash rate to consistently produce longer chains and reverse transactions. Economically infeasible on large networks like Bitcoin.
8 Sybil Resistance via Hash Power Creating millions of identities is cheap, but PoW requires real physical resources (hardware + electricity) for each unit of voting power — Sybil resistance is built-in.

↓

⛏️ PoW Miner60% of reward
🗳️ 5 PoS Voters30% (6% each)
🏛️ Treasury / DAO10% of reward
↓
🔄 Phase 4 — Next Block
  • New PoW miner begins mining the next block
  • New ticket-holders drawn from pool for the next vote round

3. When to Use Blockchain Over Other DLTs

Use Blockchain when:

  • Multiple distrusting parties need to interact without a central arbiter — Blockchain's decentralized consensus is ideal (e.g., cross-border payments between competing banks).
  • Cryptocurrency or native token is central to the use case — blockchain's tokenomics (gas, rewards, staking) are deeply integrated.
  • Strong immutability and tamper evidence is legally or operationally required — SHA-256 chaining provides court-admissible audit trails.
  • Smart contracts with complex logic are needed — Ethereum's EVM is the most mature, battle-tested smart contract platform.
  • Public auditability is required — public blockchain provides a fully transparent, censorship-resistant record accessible to anyone.
  • Decentralization is non-negotiable — e.g., DeFi applications where censorship resistance is core to the value proposition.
  • Sequential ordering of transactions matters and must be cryptographically proven — Blockchain's block structure guarantees total ordering.

Use Alternative DLT when:

  • Very high throughput is required (millions of IoT microtransactions): Use IOTA's DAG or Hashgraph.
  • Known, regulated participants with strong identity requirements: Use Corda or Quorum (no token needed, legal entity identity built-in).
  • Privacy between transaction parties is paramount: Corda shares data only with involved parties.
  • No cryptocurrency desired — Corda and Quorum operate tokenlessly.
  • Instant finality critical — Hashgraph or Corda's notary provide stronger finality guarantees than PoW blockchain.
💡 Decision Heuristic: If your use case requires public, decentralized, permissionless operation with native tokens and smart contracts → Blockchain. If it requires high-performance, permissioned, privacy-preserving operation among known institutions → Corda / Quorum. If it requires massive IoT-scale microtransaction throughput → DAG (IOTA).

3. Cryptographic Properties That Make This Secure

  • ECDSA Signing: Each transaction signed with (r, s, v) values; anyone can verify signature using public key, but only private key holder can produce it.

2. Complete Solidity Smart Contract

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.19;

/**
 * @title RealEstateRegistry
 * @dev Manages property registration, transactions, and lease agreements
 *      focusing on security, transparency, and automation.
 * @author 23BCE0737 — BCSE329L
 */
contract RealEstateRegistry {

    // ─── ENUMS ──────────────────────────────────────────────────────────────
    enum PropertyStatus { Available, Sold, Leased, Disputed }

    // ─── STRUCTS ─────────────────────────────────────────────────────────────
    struct Property {
        uint256 id;
        string  location;        // Physical address / GPS coordinates
        uint256 price;           // Price in Wei
        address payable owner;   // Current owner's wallet address
        PropertyStatus status;
        bool    registered;
        uint256 registeredAt;    // Timestamp of registration
    }

    struct LeaseAgreement {
        uint256 propertyId;
        address tenant;
        uint256 monthlyRent;     // In Wei
        uint256 startDate;       // Unix timestamp
        uint256 endDate;         // Unix timestamp
        uint256 securityDeposit; // Held in contract until lease ends
        bool    active;
    }

    struct TransactionRecord {
        uint256 propertyId;
        address from;
        address to;
        uint256 price;
        uint256 timestamp;
    }

    // ─── STATE VARIABLES ─────────────────────────────────────────────────────
    address public admin;
    uint256 public propertyCount;
    uint256 public leaseCount;
    uint256 public txCount;

    mapping(uint256 => Property)          public properties;
    mapping(uint256 => LeaseAgreement)    public leases;
    mapping(uint256 => TransactionRecord) public transactionHistory;
    mapping(address => bool)              public verifiedOwners; // KYC-like whitelist

    // ─── EVENTS (Transparency layer — all actions permanently logged) ────────
    event PropertyRegistered(
        uint256 indexed propertyId,
        address indexed owner,
        string  location,
        uint256 price,
        uint256 timestamp
    );
    event PropertySold(
        uint256 indexed propertyId,
        address indexed previousOwner,
        address indexed newOwner,
        uint256 price,
        uint256 timestamp
    );
    event LeaseCreated(
        uint256 indexed leaseId,
        uint256 indexed propertyId,
        address indexed tenant,
        uint256 monthlyRent,
        uint256 startDate,
        uint256 endDate
    );
    event LeaseTerminated(
        uint256 indexed leaseId,
        uint256 indexed propertyId,
        uint256 timestamp
    );
    event DepositRefunded(
        uint256 indexed leaseId,
        address indexed tenant,
        uint256 amount
    );

    // ─── MODIFIERS (Security layer) ──────────────────────────────────────────
    modifier onlyAdmin() {
        require(msg.sender == admin, "RealEstate: caller is not admin");
        _;
    }

    modifier onlyPropertyOwner(uint256 _propertyId) {
        require(
            properties[_propertyId].owner == msg.sender,
            "RealEstate: caller is not property owner"
        );
        _;
    }

    modifier propertyMustExist(uint256 _propertyId) {
        require(
            properties[_propertyId].registered,
            "RealEstate: property not registered"
        );
        _;
    }

    modifier propertyMustBeAvailable(uint256 _propertyId) {
        require(
            properties[_propertyId].status == PropertyStatus.Available,
            "RealEstate: property is not available for transaction"
        );
        _;
    }

    // ─── CONSTRUCTOR ─────────────────────────────────────────────────────────
    constructor() {
        admin = msg.sender;
    }

    // ─── ADMIN FUNCTIONS ─────────────────────────────────────────────────────

    /// @notice Admin verifies a property owner's identity (simulates KYC)
    function verifyOwner(address _owner) external onlyAdmin {
        verifiedOwners[_owner] = true;
    }

    // ─── MODULE 1: PROPERTY REGISTRATION ─────────────────────────────────────

    /// @notice Register a new property on the blockchain
    /// @param _location Human-readable or GPS location string
    /// @param _price     Listing price in Wei
    /// @return propertyId The unique ID of the registered property
    function registerProperty(
        string  calldata _location,
        uint256 _price
    ) external returns (uint256 propertyId) {
        require(bytes(_location).length > 0, "RealEstate: location required");
        require(_price > 0,                  "RealEstate: price must be positive");

        propertyCount++;
        propertyId = propertyCount;

        properties[propertyId] = Property({
            id           : propertyId,
            location     : _location,
            price        : _price,
            owner        : payable(msg.sender),
            status       : PropertyStatus.Available,
            registered   : true,
            registeredAt : block.timestamp
        });

        emit PropertyRegistered(
            propertyId,
            msg.sender,
            _location,
            _price,
            block.timestamp
        );
    }

    /// @notice Owner updates listing price
    function updateListingPrice(uint256 _propertyId, uint256 _newPrice)
        external
        propertyMustExist(_propertyId)
        onlyPropertyOwner(_propertyId)
        propertyMustBeAvailable(_propertyId)
    {
        require(_newPrice > 0, "RealEstate: price must be positive");
        properties[_propertyId].price = _newPrice;
    }

    // ─── MODULE 2: PROPERTY TRANSACTION (BUY / SELL) ─────────────────────────

    /// @notice Purchase a property — payment auto-transferred to seller (AUTOMATION)
    /// @param _propertyId ID of the property to purchase
    function buyProperty(uint256 _propertyId)
        external
        payable
        propertyMustExist(_propertyId)
        propertyMustBeAvailable(_propertyId)
    {
        Property storage prop = properties[_propertyId];

        require(msg.sender != prop.owner, "RealEstate: owner cannot buy own property");
        require(
            msg.value >= prop.price,
            "RealEstate: insufficient ETH sent; must send >= listing price"
        );

        address payable previousOwner = prop.owner;
        uint256 salePrice = prop.price;

        // ── State changes BEFORE external calls (Checks-Effects-Interactions) ──
        prop.owner  = payable(msg.sender);
        prop.status = PropertyStatus.Sold;
        prop.price  = 0; // Clear listing price after sale

        // ── Record transaction history ──
        txCount++;
        transactionHistory[txCount] = TransactionRecord({
            propertyId : _propertyId,
            from       : previousOwner,
            to         : msg.sender,
            price      : salePrice,
            timestamp  : block.timestamp
        });

        // ── Emit event for transparency ──
        emit PropertySold(
            _propertyId,
            previousOwner,
            msg.sender,
            salePrice,
            block.timestamp
        );

        // ── Automated ETH transfer to previous owner ──
        previousOwner.transfer(salePrice);

        // ── Refund any excess ETH sent ──
        uint256 excess = msg.value - salePrice;
        if (excess > 0) {
            payable(msg.sender).transfer(excess);
        }
    }

    // ─── MODULE 3: LEASE AGREEMENTS ──────────────────────────────────────────

    /// @notice Create a lease agreement for a property
    /// @param _propertyId   Property to lease
    /// @param _tenant       Address of the tenant
    /// @param _monthlyRent  Monthly rent in Wei
    /// @param _startDate    Lease start (Unix timestamp)
    /// @param _endDate      Lease end (Unix timestamp)
    function createLease(
        uint256 _propertyId,
        address _tenant,
        uint256 _monthlyRent,
        uint256 _startDate,
        uint256 _endDate
    )
        external
        payable
        propertyMustExist(_propertyId)
        onlyPropertyOwner(_propertyId)
        propertyMustBeAvailable(_propertyId)
    {
        require(_tenant != address(0),    "RealEstate: invalid tenant address");
        require(_tenant != msg.sender,    "RealEstate: owner cannot be tenant");
        require(_monthlyRent > 0,         "RealEstate: rent must be positive");
        require(_endDate > _startDate,    "RealEstate: invalid lease period");
        require(_startDate >= block.timestamp, "RealEstate: start date in the past");
        // Security deposit = 2 months' rent, sent by owner at lease creation
        require(msg.value >= 2 * _monthlyRent, "RealEstate: send 2 months deposit");

        leaseCount++;
        leases[leaseCount] = LeaseAgreement({
            propertyId      : _propertyId,
            tenant          : _tenant,
            monthlyRent     : _monthlyRent,
            startDate       : _startDate,
            endDate         : _endDate,
            securityDeposit : msg.value,
            active          : true
        });

        properties[_propertyId].status = PropertyStatus.Leased;

        emit LeaseCreated(
            leaseCount,
            _propertyId,
            _tenant,
            _monthlyRent,
            _startDate,
            _endDate
        );
    }

    /// @notice Terminate an active lease and refund security deposit to tenant
    /// @param _leaseId ID of the lease to terminate
    function terminateLease(uint256 _leaseId) external {
        LeaseAgreement storage lease = leases[_leaseId];

        require(lease.active, "RealEstate: lease is not active");
        require(
            msg.sender == lease.tenant ||
            msg.sender == properties[lease.propertyId].owner ||
            msg.sender == admin,
            "RealEstate: not authorized to terminate"
        );

        uint256 depositAmount = lease.securityDeposit;
        address tenantAddress = lease.tenant;
        uint256 propId        = lease.propertyId;

        // ── State changes first (re-entrancy protection) ──
        lease.active          = false;
        lease.securityDeposit = 0;
        properties[propId].status = PropertyStatus.Available;

        emit LeaseTerminated(_leaseId, propId, block.timestamp);

        // ── Refund security deposit to tenant ──
        if (depositAmount > 0) {
            payable(tenantAddress).transfer(depositAmount);
            emit DepositRefunded(_leaseId, tenantAddress, depositAmount);
        }
    }

    // ─── VIEW FUNCTIONS (Transparency — anyone can query) ────────────────────

    function getProperty(uint256 _propertyId)
        external view
        propertyMustExist(_propertyId)
        returns (
            string memory location,
            uint256 price,
            address owner,
            PropertyStatus status,
            uint256 registeredAt
        )
    {
        Property storage p = properties[_propertyId];
        return (p.location, p.price, p.owner, p.status, p.registeredAt);
    }

    function getLease(uint256 _leaseId)
        external view
        returns (
            uint256 propertyId,
            address tenant,
            uint256 monthlyRent,
            uint256 startDate,
            uint256 endDate,
            bool    active
        )
    {
        LeaseAgreement storage l = leases[_leaseId];
        return (l.propertyId, l.tenant, l.monthlyRent,
                l.startDate, l.endDate, l.active);
    }

    function getTransactionRecord(uint256 _txId)
        external view
        returns (
            uint256 propertyId,
            address from,
            address to,
            uint256 price,
            uint256 timestamp
        )
    {
        TransactionRecord storage t = transactionHistory[_txId];
        return (t.propertyId, t.from, t.to, t.price, t.timestamp);
    }
}

3. Security Mechanisms Used in the Contract

Answer — Blockchain Challenges and How to Address Them

1. Scalability Challenge (The Blockchain Trilemma)

Vitalik Buterin identified that blockchains cannot simultaneously achieve all three: Decentralization + Security + Scalability. Optimizing for two weakens the third.

Challenge Current Limitation Solutions
Low TPS Bitcoin: ~7 TPS; Ethereum: ~15–30 TPS vs Visa: 24,000 TPS Layer-2: Rollups (Optimistic, ZK-Rollups) batch 1000s of txns off-chain → post proof on L1. Polygon achieves 65,000 TPS. Sharding: Ethereum's Danksharding splits state across shards for parallel processing.
Block Size Debate Small blocks = secure but slow; large blocks = fast but centralize Segregated Witness (SegWit) in Bitcoin: separates signature data from Tx data → effectively doubles block capacity without increasing size limit

2. Energy Consumption Challenge

  • Problem: Bitcoin's PoW consumes ~150 TWh/year (comparable to Poland). ASIC mining farms have a massive carbon footprint.
  • Solution: Transition to Proof of Stake — Ethereum's Merge (Sept 2022) reduced energy consumption by ~99.95%. PoS validators stake ETH instead of burning electricity.
  • Alternative: Proof of Space (Chia) — uses storage capacity instead of computation; far more energy-efficient.

Vulnerability Example Attack Solution

Oracle Manipulation Flash loan attacks manipulate on-chain price oracles Chainlink TWAP (Time-Weighted Average Price) oracles; multiple oracle sources

  • Problem: Ethereum, Solana, Bitcoin, Hyperledger cannot natively communicate. Siloed value and data.
  • Solution — Cross-chain Bridges: Lock assets on Chain A → mint equivalent on Chain B (e.g., wBTC = Bitcoin on Ethereum).
  • Solution — Polkadot: Relay chain + parachains architecture — different blockchains communicate via shared relay chain security.
  • Solution — Cosmos IBC (Inter-Blockchain Communication): Standardized protocol for cross-chain token and message passing.
  • Solution — Hyperledger Cactus: Enterprise cross-ledger integration framework.

Step 8 — Load Distribution and Scalability

  • Read Load Balancing: Place Nginx/HAProxy in front of RPC nodes; round-robin or least-connections routing distributes queries across N read-replica nodes.
  • Write Routing: All write transactions (state changes) must go through validator/miner nodes; smart routing separates read and write paths.
  • Sharding (Ethereum Danksharding): Divide state into 64 shards; each shard processed by a subset of validators; overall throughput multiplied by shard count.
  • Redis Caching: Cache frequently-queried block data, transaction receipts, and contract state locally → reduces RPC load on full nodes.

Step 9 — Fault Tolerance Mechanisms

  • BFT guarantee: With PBFT/IBFT: network continues as long as <⅓ of validators are faulty. With 7 validators: survives 2 simultaneous failures.
  • Geographic redundancy: Distribute validators across separate data centers / AWS regions → no single data center failure can take down consensus.
  • Automatic Restart: Use systemd services with Restart=always → node auto-restarts after crashes.
  • Snapshots: Periodic state snapshots → allows new nodes to sync quickly without replaying all historical blocks from genesis.
