📌 Overview & Design Challenges
  • Embedded System: A dedicated computing system designed to perform specific tasks, integrated into a larger mechanical/electrical system. Examples: washing machine, ECU, ATM.
  • Key characteristics: Real-time operation, low power, limited memory, reliability, specific I/O interfaces.
  • Design challenges: Power constraints, real-time deadlines, memory limitations, thermal management, hardware-software co-design, cost, time-to-market.
  • Embedded vs. General-purpose: Embedded = task-specific, predictable, resource-constrained. GP = flexible, resource-rich, OS-heavy.
  • Harvard Architecture: Separate instruction and data memory buses → faster execution. Used in most microcontrollers (8051, PIC, AVR).
  • Von Neumann Architecture: Single shared bus → simpler design. Used in ARM Cortex-M (some variants).
  • Design metrics: NRE cost, unit cost, performance, power, flexibility, time to prototype, testability.
⚙️ Embedded Processor Technology
  • Microprocessor (MPU): CPU only on chip — needs external RAM, ROM, I/O. General-purpose. e.g., Intel 8086.
  • Microcontroller (MCU): CPU + RAM + ROM + I/O + Timers on single chip. e.g., 8051, PIC16F877A.
  • DSP (Digital Signal Processor): Optimized for multiply-accumulate (MAC) operations. Used in audio, communication.
  • FPGA: Reconfigurable logic fabric. Highest performance, highest power, programmable hardware.
  • ASIC: Application Specific IC — best performance and power but high NRE cost, no reconfigurability.
  • SoC (System-on-Chip): CPU + DSP + memory + peripherals on single die. e.g., Raspberry Pi BCM2837, Qualcomm Snapdragon.
  • RISC vs CISC: RISC (ARM, PIC) — fewer instructions, fixed-length, fast; CISC (x86) — complex instructions, variable-length.

🏗️ Microcontroller Architecture: 8051, PIC, ARM
8051 Architecture›
  • CPU: 8-bit Harvard architecture, 8-bit data bus, 16-bit address bus.
  • Memory: 4KB internal ROM, 128 bytes internal RAM, expandable to 64KB external ROM/RAM.
  • I/O: Four 8-bit bidirectional ports: P0, P1, P2, P3. P0 also acts as multiplexed address/data bus.
  • Timers: Two 16-bit timers (Timer 0 and Timer 1). Can operate in 4 modes (0–3).
  • UART: Full-duplex serial communication. Baud rate set by Timer 1.
  • Interrupts: 5 interrupt sources — INT0, INT1, Timer0, Timer1, Serial Port.
  • Clock: Typical 11.0592 MHz (chosen for accurate baud rates). Machine cycle = 12 clock cycles.
  • Special Function Registers (SFRs): ACC (Accumulator), B-register, PSW, SP, DPTR, TCON, TMOD, SCON, SBUF.
  • PSW flags: CY (Carry), AC (Auxiliary Carry), OV (Overflow), P (Parity), F0, RS0, RS1 (register bank select).
  • Register banks: 4 banks × 8 registers (R0–R7) in RAM addresses 00H–1FH.
PIC Architecture›
  • PIC: Peripheral Interface Controller by Microchip Technology. RISC-based Harvard architecture.
  • PIC16F877A: 8-bit MCU, 20 MHz max, 256 bytes EEPROM, 368 bytes RAM, 8KB Flash.
  • Instruction set: Only 35 instructions (RISC). All instructions execute in 1–2 cycles.
  • Pipeline: 2-stage pipeline — fetch and execute (overlap). Single-cycle throughput.
  • I/O Ports: PORTA (RA0–RA5), PORTB (RB0–RB7), PORTC, PORTD, PORTE.
  • ADC: 10-bit A/D converter built-in. PIC16F877A has 8 channels.
  • Timers: TMR0 (8-bit), TMR1 (16-bit), TMR2 (8-bit with PR2 period register).
  • Watchdog Timer (WDT): RC oscillator based, ~18 ms period. Prescaler extends to 2.3 seconds.
  • TRIS register: Data direction register — 1 = input, 0 = output.
  • Banking: 4 register banks — bank select bits RP0, RP1 in STATUS register.
ARM Architecture›
  • ARM: Advanced RISC Machine. Load-store architecture — operations only on registers.
  • Registers: 16 general-purpose registers (R0–R15). R13 = SP, R14 = LR (Link Register), R15 = PC.
  • Data widths: ARM = 32-bit; Thumb = 16-bit compressed instructions; Thumb-2 = mixed 16/32-bit.
  • Cortex families: A-series (Application — phones), R-series (Real-time — automotive), M-series (Microcontroller — embedded).
  • Pipeline: ARM7 = 3-stage (Fetch, Decode, Execute); Cortex-M3 = 3-stage; Cortex-A9 = 8-stage superscalar.
  • Exception levels: EL0 (User), EL1 (OS), EL2 (Hypervisor), EL3 (Secure Monitor) in ARMv8 AArch64.
  • AMBA bus: AHB (Advanced High-performance Bus), APB (Advanced Peripheral Bus) for SoC interconnect.
  • Condition codes: All ARM instructions can be conditionally executed using 4-bit condition field — reduces branch overhead.

💾 Memory Interfacing
  • Memory types: ROM (Mask ROM, EPROM, EEPROM, Flash) for program; RAM (SRAM, DRAM) for data.
  • Address decoding: Full decoding (no aliasing, complex), Partial decoding (aliasing, simpler), Block decoding.
  • CS generation: Using AND/NAND gates, 74LS138 (3-to-8 decoder) for chip select generation.
  • 8051 external memory: ALE pin latches low byte of address. PSEN# for program memory, RD#/WR# for data memory.
  • Memory map: 8051: 0000H–FFFFH (64KB program ROM), 0000H–FFFFH (64KB external RAM).
  • Wait states: Added when slow memory used with fast CPU. Wait = (t_mem – t_cycle) / t_clk cycles.
Memory Address Range
Start address = Base
End address = Base + (2address_lines – 1)
Memory size = 2number_of_address_lines bytes
Number of chips needed = Total memory size / Chip size

A 32KB external SRAM chip (2732) with 15 address lines is to be interfaced with 8051 at addresses 8000H to FFFFH. The 8051 runs at 11.0592 MHz. The SRAM has an access time of 150 ns. Determine: (a) Number of chips needed, (b) Chip select logic, (c) Required wait states.
Given: Total range = 8000H to FFFFH Size = FFFFH − 8000H + 1 = 0x8000 = 32768 bytes = 32KB Chip size = 32KB (15 address lines → 2¹⁵ = 32768 bytes) (a) Number of chips needed: N = Total memory needed / Chip size N = 32KB / 32KB = 1 chip (b) Chip Select Logic: Address 8000H = 1000 0000 0000 0000 B A15 = 1, A14–A0 connect to chip address pins CS# = A15_BAR (Inverted A15) When A15 = 1: CS# = 0 → chip enabled for 8000H–FFFFH ✓ (c) Wait States: Clock frequency = 11.0592 MHz Clock period = 1/11.0592 × 10⁶ ≈ 90.5 ns Machine cycle = 12 × 90.5 = 1086 ns 8051 data read timing ≈ 2 machine cycles = 2172 ns (plenty) SRAM access time = 150 ns < 1086 ns (1 machine cycle) ∴ Wait states = 0 (no wait state required) The 8051 at 11.0592 MHz is slow enough for 150 ns SRAM.

ADC — Analog to Digital Converter

Digital Output = round( Vin / Vref × 2n )
% Resolution = (1 / 2n) × 100
Quantization Error = ±½ LSB = ± Vref / (2 × 2n)

Conversion time (Successive Approx) = n × Tclk

Vout = (D / 2n) × Vref
Vout = Vref × (bn-1/2 + bn-2/4 + ... + b0/2n)
LSB weight = Vref / 2n
Full-scale output = Vref × (1 – 2-n)
Settling time: time for output to reach final value within ½ LSB
🔢 Numerical — ADC Multi-part Problem
A 12-bit ADC with V_ref = 5.0 V is used to measure a sensor voltage. The sensor outputs 3.67 V. Find: (a) Resolution in mV/LSB, (b) Digital output code in decimal and hex, (c) Quantization error, (d) SNR in dB, (e) Minimum sampling rate if signal bandwidth is 4 kHz, (f) Conversion time for a 200 kHz SAR clock.
n = 12 bits, V_ref = 5.0 V, V_in = 3.67 V (a) Resolution: Step = V_ref / (2ⁿ – 1) = 5.0 / (4096 – 1) = 5.0 / 4095 Step ≈ 1.221 mV/LSB (b) Digital Output: D = round(V_in / V_ref × 2ⁿ) D = round(3.67 / 5.0 × 4096) D = round(0.734 × 4096) D = round(3006.46) = 3006 decimal = 0xBBE (hex) Verify: 3006 × 1.221 mV = 3.669 V ≈ 3.67 V ✓ (c) Quantization Error: Q_error = ± ½ LSB = ± 1.221/2 = ± 0.610 mV As % of full scale = ±0.610 / 5000 × 100 = ±0.0122% (d) SNR: SNR = 6.02 × n + 1.76 = 6.02 × 12 + 1.76 SNR = 72.24 + 1.76 = 74.0 dB (e) Nyquist sampling rate: f_sample ≥ 2 × f_max = 2 × 4000 = 8000 Hz (minimum) In practice, use 2.5–4× → 10–16 kHz recommended (f) Conversion time (SAR — Successive Approximation): T_clk = 1 / 200,000 Hz = 5 µs per clock t_conv = n × T_clk = 12 × 5 µs = 60 µs Max throughput = 1/60µs ≈ 16,667 conversions/second

An 8-bit R-2R ladder DAC has V_ref = 10 V. Find the output voltage for: (a) input code = 10110100, (b) input code = 11111111 (full scale), (c) input code = 10000000 (midscale). Also find the LSB weight and percentage resolution.

⏱️ Timers, Watchdog Timer & Counters
  • 8051 Timer modes: Mode 0 (13-bit), Mode 1 (16-bit), Mode 2 (8-bit auto-reload), Mode 3 (split timer).
  • Timer clock source: Internal: f_osc/12. External: T0 (P3.4), T1 (P3.5) pins.
  • TMOD register: Upper nibble = Timer1 config, Lower nibble = Timer0 config. GATE, C/T#, M1, M0 bits.
  • TCON register: TR0, TR1 (run bits), TF0, TF1 (overflow flags), IE0, IE1, IT0, IT1.
  • Watchdog Timer: Resets MCU if not refreshed (kicked) within timeout. Prevents software hang. Must write specific sequence to reset it.
  • PIC WDT: Uses internal RC oscillator (≈1.8 ms base). Prescaler ratio 1:1 to 1:128 extends timeout up to 2.3 s.
  • Counter mode: C/T# bit = 1. Counts external pulses on T0/T1 pins (falling edge).
8051 Timer Formulas
Timer count per second = fosc / 12
Time per count = 12 / fosc [Machine cycle time]

Mode 1 (16-bit): TH|TL initial = 65536 – (t_delay × fosc / 12)
Mode 2 (8-bit auto-reload): TH = TL = 256 – (t_delay × fosc / 12)

Baud Rate (UART, Timer 1 Mode 2, SMOD=0):
Baud = fosc / (384 × (256 – TH1))
TH1 = 256 – fosc / (384 × baud_rate)

If SMOD=1 (double baud rate):
Baud = fosc / (192 × (256 – TH1))
🔢 Numerical — Timer & Baud Rate (8051)
An 8051 runs at f_osc = 11.0592 MHz. (a) Find TH1 and TL1 value for Timer 1 in Mode 2 to generate 9600 baud UART, SMOD=0. (b) Find the Timer 0 initial count (TH0:TL0) in Mode 1 to generate a 50 ms delay. (c) How many Timer 0 overflows are needed to generate a 1-second delay using the 50 ms sub-delay? (d) What is the maximum delay achievable with Timer 0 in Mode 1 at this clock?
f_osc = 11.0592 MHz, Machine cycle = 12/11.0592 MHz = 1.085 µs (a) TH1 for 9600 baud (SMOD=0): TH1 = 256 – f_osc / (384 × baud) TH1 = 256 – 11,059,200 / (384 × 9600) TH1 = 256 – 11,059,200 / 3,686,400 TH1 = 256 – 3 = 253 = 0xFD (TL1 = TH1 = 0xFD for Mode 2 auto-reload) (b) Timer 0, Mode 1, delay = 50 ms: Counts needed = t_delay / (12/f_osc) Counts = 50 × 10⁻³ / (12 / 11,059,200) Counts = 0.050 / 1.0851 × 10⁻⁶ Counts = 46,080 counts Initial value = 65536 – 46080 = 19456 = 0x4C00 ∴ TH0 = 0x4C = 76, TL0 = 0x00 = 0 (c) Overflows for 1-second delay: Each overflow = 50 ms Overflows needed = 1000 ms / 50 ms = 20 overflows Use a software counter variable; decrement from 20 in ISR. (d) Maximum Mode 1 delay (TH0=TL0=00H, counts 65536): t_max = 65536 × (12 / 11,059,200) t_max = 65536 × 1.0851 µs t_max ≈ 71,110 µs = ≈ 71.11 ms
📡 UART Communication
  • UART frame: Start bit (1, LOW) + Data bits (5–9) + Parity bit (optional) + Stop bit(s) (HIGH). LSB sent first.
  • Baud rate: Bits per second (bps). Bit time = 1/baud_rate seconds.
  • SCON (8051): SM0, SM1 (mode), SM2 (multiprocessor), REN (receive enable), TB8, RB8, TI, RI.
  • Modes: Mode 0 (shift register, 8-bit), Mode 1 (UART, 8-bit + start/stop), Mode 2 (9-bit, fixed baud), Mode 3 (9-bit, variable baud).
  • Parity: Even parity: number of 1s (including parity bit) is even. Odd parity: number of 1s is odd.
  • RS-232 levels: Logic 1 = –3 to –15V, Logic 0 = +3 to +15V. MAX232 chip converts TTL ↔ RS-232.
  • Oversampling: UART receiver samples at 16× baud rate for noise immunity. Majority vote of bits 7, 8, 9.
UART Data Transfer Time
Bit time = 1 / Baud_rate seconds
Frame size = 1 (start) + data_bits + parity + stop_bits
Frame time = Frame_size / Baud_rate seconds
Time to transmit N bytes = N × frame_time

Effective throughput = data_bits / frame_size × baud_rate bps
🔢 Numerical — UART Timing
A UART is configured at 115200 baud with 8 data bits, even parity, 1 stop bit (8E1 format). Find: (a) Bit time, (b) Frame duration, (c) Time to transmit 512 bytes of data, (d) Effective data throughput in bps, (e) Number of frames that can be transmitted per second.
Baud = 115200, Frame = 1 start + 8 data + 1 parity + 1 stop = 11 bits (a) Bit time: t_bit = 1 / 115200 = 8.68 µs (b) Frame duration: t_frame = 11 / 115200 = 95.49 µs (c) Time for 512 bytes: t_total = 512 × 95.49 µs = 48,890 µs = ≈ 48.89 ms (d) Effective data throughput: Throughput = (data_bits / frame_size) × baud Throughput = (8/11) × 115200 = 0.7273 × 115200 Throughput ≈ 83,782 bps ≈ 83.8 kbps (e) Frames per second: FPS = 115200 / 11 = 10,472 frames/sec i.e., 10,472 bytes/sec ≈ 10.2 KB/s
🌡️ Sensors & Actuators
  • Sensor types: Temperature (LM35, DS18B20, RTD, Thermocouple), Pressure (piezoelectric), Humidity (capacitive), Proximity (IR, ultrasonic), Light (LDR, photodiode).
  • LM35: 10 mV/°C linear output, 0°C = 0V. Range –55°C to +150°C. No calibration needed.
  • RTD (PT100): Resistance = 100Ω at 0°C. α = 0.00385 Ω/Ω/°C. R(T) = 100(1 + αT).
  • Thermocouple: Seebeck effect — voltage proportional to temperature difference. Needs cold junction compensation.
  • Actuator types: DC motor, Servo motor, Stepper motor, Relay, Solenoid, LED, Buzzer.
  • H-bridge: Controls DC motor direction and speed. Four switches; PWM on enable controls speed.
  • PWM for servo: Period = 20 ms (50 Hz). Pulse width: 1 ms = 0°, 1.5 ms = 90°, 2 ms = 180°.
  • Stepper motor: Steps per revolution (typical 200 steps = 1.8°/step). Full step, half step, microstepping.
  • Encoder: Rotary encoder — quadrature signals (A, B). Direction determined by phase relationship. Pulses count gives position.
RTD & Sensor Formulas
RTD: R(T) = R₀ × (1 + α × T) [T in °C, R₀ = 100Ω for PT100]
LM35 output: Vout = 10 mV/°C × T
Temperature from ADC: T = (ADC_code × V_ref) / (2ⁿ × 10 mV)

Stepper speed (RPM): RPM = (Steps/sec × 60) / Steps_per_rev
Stepper step delay (ms) = 60,000 / (RPM × steps_per_rev)

PWM Duty cycle = t_on / T_period × 100%
PWM frequency = 1 / T_period

🏧 ATM Architecture
  • ATM Components: Card reader, PIN pad, Display (LCD/CRT), Receipt printer, Cash dispenser, Network module, Host processor, UPS, Camera.
  • ATM processor: Typically Intel Atom/ARM-based embedded PC with OS (Windows XP Embedded or Linux).
  • Software layers: Application layer → XFS (eXtensions for Financial Services) → Device drivers → Hardware.
  • Communication: TCP/IP over dedicated leased line or VPN to bank host. Uses ISO 8583 message format for transactions.
  • Security: HSM (Hardware Security Module) for PIN encryption (Triple DES/AES). SSL/TLS for network. EMV chip card.
  • Cash dispenser: Cassettes holding 2000–2500 notes each. Mechanical pick/transport/detect mechanisms. Shutter for security.
  • Transaction flow: Card insertion → Magnetic stripe/chip read → PIN entry (encrypted) → Host verification → Cash dispense → Eject card → Print receipt.
  • Uptime requirement: 99.9% availability = max 8.76 hours downtime/year.
  • Challenges: Physical security, network reliability, power backup, vandalism, skimming attacks.
📱 Handheld Devices & Data Compressor
  • Handheld constraints: Small form factor, battery powered (mAh matters), limited thermal dissipation, touch/key I/O, wireless connectivity.
  • Mobile SoC: CPU cluster + GPU + DSP + NPU + modem + PMIC on one die. e.g., ARM big.LITTLE architecture.
  • big.LITTLE: Big cores (Cortex-A78) for performance + Little cores (Cortex-A55) for efficiency. OS scheduler assigns tasks dynamically.
  • Power states: Active, Idle, Sleep, Deep Sleep, Hibernate. Power gating and clock gating used to save power.
  • Memory hierarchy in handhelds: Registers → L1/L2/L3 cache → LPDDR4/5 RAM → eMMC/UFS Flash.
  • Data Compressor architecture: Input buffer → Compression engine (LZW, Huffman, Deflate) → Output buffer → Storage/Transmit.
  • Lossless compression: Huffman coding, LZW (Lempel-Ziv-Welch), RLE (Run Length Encoding). Used for text, executables.
  • Lossy compression: DCT (Discrete Cosine Transform) for JPEG, MPEG, MP3. Quantization introduces loss.
  • Compression ratio: CR = Original size / Compressed size. Higher CR = more compression.
  • Huffman coding: Variable-length codes. Frequent symbols get shorter codes. Prefix-free binary tree.
📷 Image Capturing Devices — Architecture
  • Image sensor types: CCD (Charge-Coupled Device) — low noise, high quality; CMOS — lower power, faster, cheap, now dominant.
  • Bayer pattern: RGGB arrangement on CMOS sensor. 50% green (human eye most sensitive to green). Demosaicing to reconstruct full RGB.
  • ISP (Image Signal Processor): Dedicated processor for demosaicing, noise reduction, auto-white balance, auto-exposure, HDR processing.
  • MIPI CSI-2: Camera Serial Interface — standard interface between image sensor and application processor. Differential signaling, 1–4 lanes.
  • Image pipeline: Sensor → ADC → ISP → Compression (JPEG/HEIF) → Memory → Display.
  • Resolution: Megapixels = (horizontal pixels × vertical pixels) / 1,000,000.
  • Frame rate: fps = 1 / frame_time. 4K@60fps = massive data bandwidth needed.
  • Challenges: Power dissipation from high-res sensors, heat in compact body, ISP computational load, storage bandwidth.

📜 Evolution & Modelling of Embedded Programs
  • Evolution: Machine code → Assembly → Embedded C → C++ → RTOS-based → Model-based (Simulink, LabVIEW).
  • Assembly advantages: Full hardware control, deterministic timing, smallest code size.
  • Embedded C: Standard C + hardware-specific extensions (volatile, bit fields, inline assembly, fixed-size types from stdint.h).
  • volatile keyword: Tells compiler not to cache the variable — read from hardware register every time. Essential for hardware registers and ISR-shared variables.
  • Cross-compiler: Compiler runs on host PC but generates code for target MCU (e.g., arm-gcc on Linux compiling for Cortex-M).
  • Build process: Source (.c) → Preprocessor → Compiler → Assembler (.o) → Linker (ld) → Locator → Binary/HEX.
  • Linker script: Defines memory regions (FLASH, RAM), section placement (.text, .data, .bss, .stack).
  • Program models: Round-robin (polling loop), Round-robin with interrupts, Function queue scheduling, RTOS-based.
  • Modelling tools: UML (Unified Modelling Language), State machine diagrams, Data flow diagrams, Simulink (MBD).
  • FSM (Finite State Machine): States + transitions + actions. Essential for embedded control — e.g., vending machine, traffic light controller.
⚡ Code Optimization Techniques
  • Loop unrolling: Reduce loop overhead by manually replicating loop body. Increases code size but reduces branch penalty.
  • Strength reduction: Replace expensive operations with cheaper ones. Division by 2 → right shift. Multiplication by constant → add+shift.
  • Inline functions: inline keyword eliminates function call overhead (push/pop registers). Trade: code bloat.
  • Register variables: register int x hints to compiler to keep in CPU register (modern compilers may ignore this).
  • Avoid float in MCU: Integer arithmetic is 10–100× faster than software floating-point on MCUs without FPU. Use fixed-point (Q notation).
  • Bit manipulation: Use bitwise operations (|, &, ^, ~, <<,>>) for hardware register access — faster and more precise than read-modify-write using arithmetic.
  • Compiler optimization levels: -O0 (no opt), -O1 (basic), -O2 (moderate, default), -O3 (aggressive), -Os (size), -Ofast (unsafe).
  • Memory optimization: Pack structs with __attribute__((packed)), use bit-fields for flags, avoid global variables (hard to optimize), use const for ROM storage.
  • Cache optimization: Spatial locality (access sequential memory), Temporal locality (reuse recent data). Pad structs to cache line boundaries.
  • Dead code elimination: Compiler removes unreachable code. Ensure no side-effects suppressed by volatile.

📊 Classification & Issues in Real-Time Systems
  • Hard Real-Time: Missing deadline = system failure. Examples: airbag controller, nuclear plant control, pacemaker.
  • Soft Real-Time: Missing deadline = degraded performance (not catastrophic). Examples: video streaming, online gaming, ATM display.
  • Firm Real-Time: Results after deadline are useless but not catastrophic. Example: stock trading system.
  • Periodic task: Arrives at fixed interval T (period). Deadline D often = T. Execution time = C (WCET).
  • Aperiodic task: Arrives at random intervals. Soft deadline or no deadline. Background tasks.
  • Sporadic task: Arrives at random intervals but with hard deadline. Minimum inter-arrival time guaranteed.
  • WCET (Worst Case Execution Time): Upper bound on task execution time. Must be known for schedulability analysis.
  • Key issues in RTS: Priority inversion, deadlock, unbounded priority inversion, jitter, latency, synchronization, shared resource access.
  • Priority Inversion: Low-priority task holds resource needed by high-priority task — medium-priority task preempts → high-priority blocked.
  • Priority Inheritance Protocol (PIP): Temporarily boost low-priority task's priority to that of highest waiting task.
  • Priority Ceiling Protocol (PCP): Each resource has ceiling = max priority of tasks using it. Task can lock resource only if priority > all locked resource ceilings.
  • Preemptive vs. Non-preemptive: Preemptive RTOS allows higher-priority task to interrupt running task. Non-preemptive = cooperative (task must yield).
📐 RMS — Rate Monotonic Scheduling
  • RMS: Priority assigned based on period — shorter period = higher priority. Fixed (static) priority. Preemptive.
  • Optimal: RMS is optimal among all fixed-priority algorithms — if any fixed-priority algorithm can schedule a task set, RMS can too.
  • Assumptions: Tasks periodic, independent, known WCET, relative deadline = period, no shared resources, context switch time negligible.
  • Utilization bound: Liu & Layland (1973) — n tasks are schedulable if U ≤ n(2^(1/n) – 1). As n→∞, bound → ln(2) ≈ 0.693 (69.3%).
  • Sufficient condition: If U ≤ n(2^(1/n)–1), the task set is guaranteed schedulable under RMS.
  • Necessary condition: U ≤ 1.0 always required. Tasks might still be schedulable even if U > bound — need response time analysis.
  • Response Time Analysis (RTA): Exact schedulability test. Compute worst-case response time R_i iteratively.
RMS Key Formulas
CPU Utilization: U = Σᵢ (Cᵢ / Tᵢ) [Cᵢ=WCET, Tᵢ=Period]

Liu-Layland Bound: U ≤ n × (2^(1/n) – 1)
n=1 → 1.000, n=2 → 0.828, n=3 → 0.780, n→∞ → 0.693

Response Time Analysis (iterative):
Rᵢ⁽⁰⁾ = Cᵢ
Rᵢ⁽ᵏ⁺¹⁾ = Cᵢ + Σⱼ∈hp(i) ⌈ Rᵢ⁽ᵏ⁾ / Tⱼ ⌉ × Cⱼ
[hp(i) = set of tasks with higher priority than i]
Iterate until Rᵢ⁽ᵏ⁺¹⁾ = Rᵢ⁽ᵏ⁾ → converged, or Rᵢ > Dᵢ → infeasible

Hyperperiod = LCM(T₁, T₂, ..., Tₙ)
Number of instances of task i in hyperperiod = LCM / Tᵢ
📐 EDF — Earliest Deadline First Scheduling
  • EDF: Dynamic priority algorithm. Task with earliest absolute deadline gets highest priority. Priority changes at each scheduling point.
  • Optimal: EDF is optimal among all scheduling algorithms (preemptive, uniprocessor). Can achieve 100% utilization.
  • Schedulability condition: U = Σ(C_i/T_i) ≤ 1.0 for preemptive EDF (sufficient AND necessary for periodic tasks with D=T).
  • EDF vs RMS: EDF better utilization (100% vs 69.3%), but dynamic priority = higher runtime overhead. RMS = simpler, predictable, analysis friendly.
  • Overload behavior: EDF degrades gracefully under overload (may miss some deadlines). RMS prioritizes high-freq tasks (lower-priority tasks always miss).
  • Absolute deadline: d_i = r_i + D_i where r_i = release time (arrival), D_i = relative deadline.
  • Laxity (Slack): L = d_i – t – C_remaining. LLF (Least Laxity First) — alternate to EDF. Same complexity, more context switches.
EDF & General Scheduling Formulas
EDF schedulable: U = Σ (Cᵢ/Tᵢ) ≤ 1.0
Absolute deadline: dᵢ = release_time + relative_deadline
Laxity: L(t) = dᵢ – t – C_remaining

Processor demand (DBF — Demand Bound Function):
dbf(t) = Σᵢ ⌊(t + Tᵢ – Dᵢ)/Tᵢ⌋ × Cᵢ ≤ t for all t > 0

Response time (for EDF, simplified):
Rᵢ = Cᵢ + I_i (interference from higher-priority tasks)

Context switch overhead consideration:
Effective utilization = Σ(Cᵢ/Tᵢ) + n × (2 × t_cs)/T_min
[t_cs = context switch time, T_min = smallest period]

🖥️ eCOS, POSIX & Protothreads
  • eCOS (Embedded Configurable OS): Open-source RTOS. Highly configurable — only include needed components. RedBoot bootloader companion. Used in networking, consumer electronics.
  • eCOS scheduler: Multi-level queue (MLQ) scheduler with bitmap priority. 32 or 64 priority levels. O(1) scheduling.
  • POSIX (Portable Operating System Interface): IEEE standard defining OS interface for portability. POSIX.1b includes real-time extensions: POSIX timers, signals, scheduling (SCHED_FIFO, SCHED_RR).
  • POSIX thread (pthread): pthread_create, pthread_join, pthread_mutex_lock/unlock, pthread_cond_wait/signal. Used in Linux embedded systems.
  • SCHED_FIFO: Real-time fixed-priority FIFO. No time slicing within same priority. Runs until blocks or yields.
  • SCHED_RR: Real-time round-robin. Time slice (quantum) among same-priority tasks. Can preempt by higher priority.
  • Protothreads: Extremely lightweight, stackless threads by Adam Dunkels. Uses C macros (PT_BEGIN, PT_WAIT_UNTIL, PT_END). No context switch overhead. Used in TinyOS, Contiki for sensor nodes.
  • Protothreads vs RTOS threads: Protothreads = cooperative, no stack per thread, minimal RAM. RTOS threads = preemptive, each has own stack (200B–4KB typical).

🔗 I2C — Inter-Integrated Circuit
  • I2C: 2-wire synchronous serial bus: SDA (data) and SCL (clock). Half-duplex. Multi-master, multi-slave.
  • Addressing: 7-bit address (128 devices) + 1 R/W bit. 10-bit addressing extension allows 1024 devices.
  • Speed modes: Standard (100 kbps), Fast (400 kbps), Fast+ (1 Mbps), High-speed (3.4 Mbps), Ultra-fast (5 Mbps).
  • Transaction: START → Address+R/W → ACK → Data byte(s) → ACK → ... → STOP.
  • START condition: SDA goes LOW while SCL is HIGH. STOP: SDA goes HIGH while SCL is HIGH.
  • Arbitration: Multi-master: loses arbitration when SDA is HIGH but detects LOW on bus. Wired-AND pull-up mechanism.
  • Clock stretching: Slave holds SCL LOW to pause transfer until ready to process.
  • Pull-up resistors: Typically 4.7 kΩ for standard mode, 1.5 kΩ for fast mode. Critical for signal integrity.
I2C Timing
Data bits per frame = 9 (8 data + 1 ACK)
START + address frame = 9 bits
Each data byte frame = 9 bits (8 data + ACK/NAK)

Transfer time for N data bytes:
t = (1 + 1 + N) × 9 bits / bit_rate
[1 START frame + 1 address frame + N data frames]

Pull-up resistor: R_min = (V_cc – V_OL) / I_sink
R_max = t_rise / (0.8473 × C_bus) [t_rise = 1 µs for SM]

🚗 CAN — Controller Area Network
  • CAN: Developed by Bosch (1986). Two-wire differential bus (CAN-H, CAN-L). ISO 11898. Used in automotive, industrial.
  • Dominant/Recessive: Dominant bit (0) wins over Recessive bit (1) — wired-AND arbitration, non-destructive.
  • Data frame: SOF (1) + Arbitration (11/29 bits) + Control (6) + Data (0–64 bytes) + CRC (15) + ACK (2) + EOF (7) = ~47–127+ bits.
  • Standard (CAN 2.0A): 11-bit identifier (2048 IDs). Extended (CAN 2.0B): 29-bit identifier (536 million IDs).
  • CAN FD (Flexible Data): Up to 8 Mbps data phase, up to 64 bytes payload. Backward compatible base.
  • Error handling: 5 error types: Bit error, Stuff error, CRC error, Form error, Acknowledgment error. Node enters Error-Active, Error-Passive, or Bus-Off state.
  • Bit stuffing: After 5 consecutive same bits, a complementary bit is stuffed (de-stuffed at receiver). Ensures transitions for sync.
  • Max bus speed vs length: 1 Mbps at 40m; 125 kbps at 500m; 10 kbps at 5km. Propagation delay limits speed × distance product.

T_bit = T_sync_seg + T_prop_seg + T_phase_seg1 + T_phase_seg2

Sample point (%) = (T_sync + T_prop + T_phase1) / T_bit × 100
Recommended sample point: 75–80%

CAN frame efficiency:
Efficiency = (Data bits) / (Total frame bits) × 100

🌾 Application Case Studies
Agriculture Sector›
  • Precision agriculture: IoT sensors (soil moisture, temperature, humidity, pH, NPK), drones for crop monitoring.
  • Key sensors: Capacitive soil moisture sensor, DHT22 (temp + humidity), SHT31, NDVI sensor (plant health via IR), flow meters.
  • Automated irrigation: MCU reads soil moisture → controls relay → drives solenoid valve → drip/sprinkler system.
  • Communication: LoRaWAN for long-range low-power field coverage (1–15 km). Zigbee for greenhouse mesh. GSM/4G for cloud upload.
  • Challenges: Outdoor harsh environment, power availability (solar+battery), weather-proofing (IP67+), wireless range, interference.
  • Smart greenhouse: Closed-loop control of temperature, humidity, CO2, lighting using PID controller on ARM MCU.
Automotive Electronics›
  • ECU (Engine Control Unit): Main embedded computer. Controls fuel injection timing, ignition timing, air-fuel ratio. Uses crank/cam position sensors, O2 sensor, MAP sensor.
  • AUTOSAR: Automotive Open System Architecture. Standardized software architecture layering: BSW (Basic Software) + RTE + Application.
  • CAN bus in car: Multiple ECUs (ABS, Airbag, Engine, Transmission, Body, Infotainment) connected on CAN. MOST bus for multimedia, FlexRay for safety-critical (X-by-wire).
  • ADAS (Advanced Driver Assistance Systems): Radar (77 GHz), LiDAR, camera fusion for adaptive cruise control, lane keeping, automatic emergency braking.
  • OBD-II (On-Board Diagnostics): Standardized diagnostic port (16-pin). Uses CAN (ISO 15765-4). PIDs (Parameter IDs) to read engine data.
  • Functional Safety: ISO 26262 standard. ASIL levels (A to D) — ASIL-D = most safety-critical (airbag, braking). Requires redundancy, monitoring, fail-safe behavior.
  • Real-time requirement: Airbag deployment: 15–30 ms from crash detection to full inflation. Hard real-time.
Consumer Electronics›
  • Smart TV: ARM SoC, DRAM, eMMC Flash, WiFi/Ethernet, HDMI, audio DSP, IR remote decoder.
  • Washing machine: 8-bit MCU (8051/PIC derivative), keypad input, motor driver (TRIAC for AC motor), water level sensor, thermistor.
  • Smart speaker: Wake word detection (edge ML on DSP), far-field mic array (beamforming), cloud NLP, codec for audio output.
  • Wearables: Ultra-low power ARM (nRF52 series), MEMS sensors (accelerometer, gyro, PPG), BLE, flexible OLED display, coin cell battery.
Industrial Controls›
  • PLC (Programmable Logic Controller): Industrial MCU designed for manufacturing. Scan cycle: Read inputs → Execute ladder logic → Write outputs. Deterministic, reliable.
  • SCADA: Supervisory Control and Data Acquisition. Monitors and controls plant-wide processes. HMI → SCADA server → PLCs → Field devices.
  • DCS (Distributed Control System): Used in chemical plants, refineries. Distributed controllers + centralized supervision. Higher integration than PLC+SCADA.
  • Industrial protocols: PROFIBUS (RS-485 based, 12 Mbps), Modbus RTU/TCP (simple, widely used), EtherCAT (ultra-fast Ethernet, sub-µs sync).
  • Hazardous environments: Intrinsic safety (limit energy to prevent ignition), explosion-proof enclosures (IP68+), wide operating temperature (-40°C to +85°C).
Medical Electronics›
  • Pacemaker: Ultra-low power ARM MCU. Senses cardiac activity → delivers ~2–5 V, 0.5–2 ms pulses if heart rate too low. Titanium casing, 10+ year battery life.
  • ECG machine: Differential amplifier (INA118) → bandpass filter (0.05–150 Hz) → ADC (16-bit, 500–1000 SPS) → DSP → Display/Store.
  • Pulse oximeter: Red (660 nm) and IR (940 nm) LEDs. Beer-Lambert law: SpO2 from ratio of AC/DC components of red and IR signals.
  • Insulin pump: Infusion pump driven by embedded controller. Calculates basal rate + bolus doses. Communicates via BLE with CGM (Continuous Glucose Monitor).
  • Regulatory: FDA Class II/III, IEC 62304 (software lifecycle), IEC 60601 (electrical safety), ISO 14971 (risk management).
  • Critical requirements: Zero tolerance for failure, redundant watchdog timers, power-fail-safe design, 10+ year operational life, biocompatibility of materials.
SpO2 Calculation (Pulse Oximeter)
R = (AC_red / DC_red) / (AC_ir / DC_ir)
SpO2 ≈ 110 – 25 × R [Empirical approximation]

Heart rate = (Number of peaks in signal) / time_window × 60 bpm
Normal SpO2: 95–100%. Below 90% = hypoxemia.
