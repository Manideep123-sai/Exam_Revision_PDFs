What is Blockchain
Blockchain is a decentralized, distributed, and immutable ledger of transactions across a peer-to-peer network. It is a collection of records (blocks) linked with each other, strongly resistant to alteration, and protected using cryptography.
Key Features
  • Decentralization — Eliminates the need for central authorities
  • Transparency — All participants can verify transactions
  • Immutability — Data cannot be altered once recorded
How It Works
  1. Someone requests a transaction
  2. Transaction is broadcast to a P2P network of nodes
  3. Network validates the transaction using known algorithms
  4. Verified transaction is combined with others into a new block
  5. New block is added to the existing blockchain (permanent & unalterable)
  6. Transaction is complete
A hacker cannot alter the blockchain because: (1) Each user has a copy of the ledger, (2) Data within blocks is encrypted by complex algorithms.
Ledgers & Distributed Ledger Technology
Distributed Ledger — A system where replicated, shared, and synchronized digital data is geographically spread across many sites, countries, or institutions. It does not require a central administrator and has no single point of failure.
  • Requires a peer-to-peer (P2P) computer network
  • Uses consensus algorithms for reliable replication across nodes
  • Most common form is blockchain (public or private)
  • Infrastructure for data management is a common barrier to implementing DLT
Traditional Ledger: Centralized, single point of failure, controlled by one entity (e.g., bank)
Distributed Ledger: Decentralized, no single point of failure, transparent, replicated across all participants
Cryptographic Hash Functions
Cryptographic Hash Function (CHF) — A mathematical algorithm that maps data of arbitrary size to a bit array of fixed size. It is a one-way function — practically infeasible to invert.
Properties of Secure Hash Functions
Property Description
Deterministic Same input always produces the same hash output
Quick Computation Hash can be computed quickly for any input
Pre-Image Resistance Given H(A), infeasible to determine A
Avalanche Effect Small change in input → huge change in hash
Collision Resistant Infeasible to find two different inputs with the same hash
Puzzle Friendly For output Y, infeasible to find input x such that H(k|x) = Y
Integrity Check: Hash the file → compare with the expected hash. If they differ, the file has been modified. A cryptographic hash is like a digital fingerprint.
How Hash Functions Work
Input bytes are processed using addition modulo 256 (wrap around to 0 when result ≥ 256). Output is a fixed-size hash regardless of input size. E.g., a 1.21 MB image → 256-bit (32-byte) hash.

SHA-256 Construction (Merkle-Damgård)
  1. Message is broken into 512-bit blocks with padding
  2. Start with 256-bit IV (Initialization Vector) + first block
  3. 768-bit string → compression function → 256-bit output
  4. Output concatenated with next block → repeat compression
  5. Final 256-bit output = the hash
Bitcoin uses SHA-256 for: (1) Mining — Proof-of-Work algorithm, (2) Creating bitcoin addresses for security and privacy.

Encryption Schemes
Encryption — Converting readable data (plaintext) into unreadable form (ciphertext) to protect from unauthorized access.
Symmetric-Key Encryption
• Same key for encrypt & decrypt
• Fast, efficient for large data
• Problem: key distribution
• Not suitable for open networks
Asymmetric-Key Encryption
• Public key (shared openly) + Private key (kept secret)
• Sender encrypts with receiver’s public key
• No need to share secret keys
• Examples: RSA, ECC
RSA
RSA — Public-key algorithm for secure data transmission. Security relies on the difficulty of factoring large numbers into prime factors. Choose primes p, q → n = p × q (public). If attacker finds p and q, the private key is broken.
Digital Signatures
Three APIs
Function Description
(sk, pk) := generateKeys(keysize) Generates secret signing key (sk) and public verification key (pk)
sig := sign(sk, message) Signs message with secret key; can be randomized
isValid := verify(pk, message, sig) Verifies signature; returns boolean (deterministic)
Requirements
  • Valid signatures must verify: verify(pk, message, sign(sk, message)) == true
  • Existentially unforgeable: Adversary who knows pk and sees signatures on chosen messages still can’t produce a valid signature on a new message
Unforgeability Game
  1. Generate keys → secret key to challenger, public key to adversary
  2. Allow attacker to get signatures on documents of his choice
  3. Attacker picks a new message M and attempts to forge a signature
  4. If verify succeeds → attacker wins (scheme is broken)

Elliptic Curve Cryptography (ECC)
ECC — A modern public-key encryption technique based on elliptic curve mathematics. Equation: y² = x³ + ax + b. Provides same security as RSA with much smaller keys.
Why ECC Matters
  • Smaller keys than RSA → faster computation
  • Lower power consumption → ideal for mobile, IoT, blockchain
  • Horizontal symmetry: any point reflected over x-axis stays on the curve
  • Any non-vertical line intersects the curve in at most three places
ECC Components
  • Private key: Random integer in a specific range (fast to generate)
  • Public key: EC point (x, y) on the curve; can be compressed to 256-bit
  • Generator Point (G): Pre-defined EC point that can generate any other point via scalar multiplication
Applications
  • Diffie-Hellman: Secret key sharing using scalar multiplication
  • ECDSA: Digital signatures used by Bitcoin and Ethereum
  • Blockchain: Bitcoin uses ECC; Ethereum 2.0 uses BLS signatures with elliptic curve pairs
CAP Theorem & Blockchain Trilemma
CAP Theorem (Brewer’s Theorem) — A distributed system cannot simultaneously guarantee all three: Consistency, Availability, and Partition Tolerance.
Consistency: All clients see the same data at the same time, regardless of which node they connect to.
Availability: Any client request gets a response, even if some nodes are down.
Partition Tolerance: System continues to work despite communication breakdowns between nodes.
During a network partition, the system must choose between Consistency and Availability. Partition Tolerance is essential in any distributed system.
Blockchain Trilemma
Derived from CAP Theorem — a blockchain cannot simultaneously achieve Scalability, Security, and Decentralization. Optimizing one requires sacrificing another.
Scalability: Ability to handle large volume of transactions efficiently
Security: Protection against attacks (double-spending, 51% attacks)
Decentralization: No single entity has complete control; ensures transparency and immutability
⭐ Exam Tip
Like CAP Theorem, the Blockchain Trilemma states it is impossible for a blockchain to simultaneously achieve all three properties. For example, increasing block size improves scalability but can reduce security by making the system more vulnerable to attacks.

Public Blockchain
A distributed ledger system without constraints and permissions. Anyone with internet access can join. The mining and trading of cryptocurrencies is the most fundamental usage. Examples: Bitcoin, Litecoin, Ethereum.
Private Blockchain
Limits access to a certain participant group that has been given authorization. Often employed by corporations, associations, or consortiums. Consensus techniques are more effective and scalable due to fewer participants.
Consortium Blockchain
A hybrid architecture combining advantages of both public and private blockchains. A consortium of organizations jointly manages and oversees the network. Offers greater privacy and scalability than public blockchains while still providing a distributed shared ledger.
Permissioned Ledger
Permissioned Ledger — A distributed ledger where access is restricted to authorized participants only. Unlike public blockchains, a governing authority controls who can read, write, or validate transactions. Combines the benefits of decentralization (data replication, no single point of failure) with enterprise-grade access control. Examples: Hyperledger Fabric, Corda, Quorum.
  • Participants are known and identified (not pseudonymous)
  • Uses efficient consensus (PBFT, RAFT) instead of energy-intensive PoW
  • Higher throughput and transaction speed than public blockchains
  • Suitable for enterprise, banking, supply chain use cases
Sidechains
Sidechain — A separate blockchain that runs in parallel to a main blockchain (parent chain) and is connected to it via a two-way peg. Assets can be transferred between the main chain and sidechain. Sidechains have their own consensus rules, enabling experimentation and scalability without affecting the main chain.
  • Assets are locked on the main chain while an equivalent amount is unlocked on the sidechain
  • Can have different consensus rules, block times, or privacy features
  • Examples: Liquid Network (Bitcoin sidechain), Polygon (Ethereum sidechain)
  • Improves scalability and enables new features without hard forking the main chain

Money & Currency
Money is any item accepted as a medium of exchange. Currency must satisfy six key properties to function as money.
Properties of Money
  • Medium of Exchange — Widely accepted for transactions

  • Durable — Can be used multiple times without degrading

  2. Bank checks if your balance > transaction amount
  3. If yes → debits your account, credits payee’s account
  4. If no → transaction is rejected

Blockchain Mining Introduction
Mining is the process of solving a mathematical puzzle (finding a valid nonce) to add a new block to the blockchain. The miner who solves it first broadcasts the block; other miners verify its validity.
  • Block No., Data, Prev Hash are all fixed
  • Nonce is the only variable miners can change
  • Goal: find a nonce such that the block’s hash meets a target (e.g., starts with enough zeros)

Distributed Identity: Public & Private Keys, Digital Identification & Wallets
Distributed Identity — In blockchain systems, identity is not managed by a central authority. Instead, each participant controls their own identity through cryptographic key pairs — a public key (shared openly, acts as an address/identity) and a private key (kept secret, used to sign transactions).
Public and Private Keys
Public Key:
• Derived from the private key using ECC
• Serves as the user’s blockchain address/identity
• Can be shared openly with anyone
• Used to verify digital signatures
• Example: Bitcoin address is hash of public key
Private Key:
• Randomly generated secret number
• Must be kept secret at all times
• Used to sign transactions (prove ownership)
• Loss = permanent loss of funds
• 256-bit number in Bitcoin (2²&sup5;&sup6; possibilities)
Digital Identification on Blockchain
  • Self-Sovereign Identity (SSI): Users own and control their digital identity without relying on centralized providers
  • Decentralized Identifiers (DIDs): W3C standard for globally unique identifiers that are cryptographically verifiable
  • Verifiable Credentials (VCs): Tamper-evident claims made by an issuer about a subject (e.g., degree certificate)
  • No single point of failure: Identity data distributed across the network, not held by one entity
Wallets as Identity Managers
A cryptocurrency wallet does not store coins — it stores private keys and manages the user’s cryptographic identity. The wallet derives public keys and addresses from the private key, signs transactions, and broadcasts them to the network.
  • Hot Wallet: Connected to internet — convenient but less secure (e.g., Metamask, Electrum)
  • Cold Wallet: Offline storage — most secure for large holdings (e.g., Ledger Nano, Trezor)
  • HD Wallet (Hierarchical Deterministic): Generates tree of keys from a single seed phrase (BIP-32); allows backup via 12/24 word mnemonic
  • Multi-sig Wallet: Requires M-of-N signatures to authorize a transaction (e.g., 2-of-3), enhancing security
⭐ Exam Key Point
In blockchain, identity is pseudonymous not anonymous — all transactions are public but linked to a key pair, not a real name. The key pair IS the identity.
Decentralized Network
Decentralized Network — A network where control, data, and decision-making are distributed among many independent nodes rather than controlled by a single central server or authority. Blockchain operates as a decentralized peer-to-peer (P2P) network.
Network Topologies
Type Description Example
Centralized Single point of control, all nodes connect to center Traditional bank servers
Decentralized Multiple hubs, some redundancy but still hierarchy Internet backbone
Distributed (P2P) Every node equal, no hierarchy, fully redundant Bitcoin network
Properties of a Blockchain P2P Network
  • No Central Authority: No single entity controls the network; rules enforced by protocol
  • Node Types: Full nodes (store entire blockchain), Light nodes (store block headers only), Miner nodes (participate in PoW)
  • Gossip Protocol: Transactions and blocks propagate across the network by nodes relaying to their peers
  • Resilience: Network continues to function even if many nodes go offline; no single point of failure
  • Trustless: Participants do not need to trust each other — trust is enforced by cryptography and consensus rules
Transaction Flow in a Decentralized Network
  1. User signs a transaction with their private key and broadcasts it to their peer nodes
  2. Nodes validate the transaction (signature, balance) and relay it to their peers (gossip propagation)
  3. Transaction enters the mempool (memory pool) of unconfirmed transactions across nodes
  4. Miners/validators select transactions from the mempool and package them into a block
  5. New block is broadcast to the network; nodes verify and append it to their copy of the blockchain
⭐ Exam Key Point
Bitcoin’s decentralized network is a permission-less P2P system — anyone can join as a node, participate in consensus, or use the network without needing approval from any authority.
Permissioned Distributed Ledger
Permissioned Distributed Ledger — A type of distributed ledger where access to participate (read, write, validate) is controlled and granted only to authorized participants. Unlike public blockchains, a central or consortium authority decides who can join the network.
Permissioned vs. Permissionless
Feature Permissioned Ledger Permissionless (Public)

Consensus Practical BFT, RAFT, or other efficient algorithms Proof of Work / Proof of Stake
Throughput High (thousands of TPS) Low (7 TPS for Bitcoin)
Energy Low (no mining puzzle) High (PoW mining)

Key Characteristics
  • Membership Service: A designated authority manages participant enrollment and issues digital certificates (e.g., Hyperledger Fabric MSP)
  • Role-Based Access: Different participants may have different permissions — some can only read, others can write transactions, others can validate
  • Privacy: Transactions can be kept private among subsets of participants using channels or private data collections
  • Auditability: All transactions are recorded with known identities, enabling regulatory compliance and audit trails
  • No Cryptocurrency Required: Many permissioned ledgers (e.g., Hyperledger Fabric) do not require a native cryptocurrency to function
Examples of Permissioned Ledgers
  • Hyperledger Fabric: Enterprise-grade permissioned blockchain by Linux Foundation; used in supply chain, finance
  • Corda: Designed for financial institutions; transactions shared only between parties involved
  • Quorum: Enterprise Ethereum variant by J.P. Morgan with privacy features
  • Ripple (XRPL): Permissioned network of trusted validators for cross-border payments
Permissioned ≠ Centralized: A permissioned ledger is still distributed across multiple independent organizations — the data is replicated and no single party has full control. The difference from public blockchains is who is allowed to participate, not that control is centralized.

Double Spending
Double Spending — The main design challenge in digital currency. A user spends the same coin twice.
GoofyCoin
  • Goofy can create new coins (signed by his key)
  • Owner can spend coins by signing a “Pay to” statement
  • Problem: Alice can send the same coin to both Bob and Chuck → double-spending attack
ScroogeCoin (Solution)
  • Scrooge publishes an append-only ledger containing all transaction history
  • CreateCoins: Valid if signed by Scrooge
  • PayCoins: Valid if: consumed coins are valid, not already consumed, total value in = total value out, signed by owners of all consumed coins
  • Coins are immutable: Created once, consumed once. Splitting/merging done via new transactions
ScroogeCoin Problem: Scrooge has too much influence — can deny service, create unlimited coins for himself, or stop updating the blockchain entirely.
Network Consensus & Sybil Attacks
Why No Persistent Identity?
  • Bitcoin is a P2P decentralized system — no central authority to assign identities
  • Sybil Attack: Malicious nodes create many copies to look like different participants, all controlled by the same adversary
  • Bitcoin provides pseudo-anonymity — transactions can be linked but real identity is hidden
Implicit Consensus Algorithm
  1. Alice creates a transaction and broadcasts to all nodes
  2. Nodes collect unconfirmed transactions
  3. A random node is selected to propose the next block
  4. Other nodes accept (extend from this block) or reject (extend from previous)
  5. Block accepted only if all transactions are valid
Double-Spend Protection
Honest nodes extend the longest valid branch. Double-spend probability decreases exponentially with number of confirmations. Common heuristic: 6 confirmations.
⭐ Key Insight
Protection against invalid transactions = cryptographic (enforced by consensus). Protection against double-spending = purely by consensus. You’re never 100% sure — guarantee is probabilistic.
Proof of Work
Proof of Work — Select nodes in proportion to computing power. Let nodes compete for the right to create a block. Makes it moderately hard to create new identities (prevents Sybil attacks).
Three Equivalent Views
  1. Select nodes in proportion to computing power
  2. Let nodes compete for the right to create a block
  3. Make it moderately hard to create new identities
Block Rewards & Miners
  • Miners validate transactions and propose new blocks
  • Block Reward: Newly minted bitcoins + transaction fees
  • Block reward halves every ~210,000 blocks (~4 years)
  • Creates economic incentive for honest behavior
Forks & Consensus Chain
Fork — When two or more miners find valid blocks at approximately the same time, creating a temporary split in the blockchain. The network resolves this using the longest-chain rule.
Types of Forks
Type Description Example
Temporary Fork Two blocks found simultaneously; resolved as one chain grows longer Normal mining operation
Soft Fork Backward-compatible protocol change; old nodes can still validate SegWit (BIP141)
Hard Fork Non-backward-compatible change; creates a permanent split Bitcoin Cash (BCH)
Longest Chain Rule: Nodes always extend the chain with the most cumulative proof-of-work. This rule ensures eventual consensus even after temporary forks. Orphaned blocks (not in longest chain) are discarded.
Finality, PoW Limitations & Alternatives
Finality in Blockchain Consensus
Finality refers to the guarantee that a transaction, once confirmed, cannot be reversed or altered. In Bitcoin, finality is probabilistic — confidence increases with each confirmation but is never 100%.

1 Low — still vulnerable to reorg Small purchases

Limitations of Proof of Work
  • Energy consumption: Enormous electricity usage for mining
  • Centralization risk: Mining pools concentrate hash power (top 4 pools ≈ 50%)
  • 51% Attack: Entity controlling majority hash power can rewrite history
  • Low throughput: Bitcoin processes only ~7 TPS
  • Hardware arms race: Only ASIC miners are competitive; excludes average users

Secret Sharing
Secret Sharing — Split a secret key S into N pieces (shares). Define threshold K such that any K shares can reconstruct the secret, but fewer than K reveal nothing. This is a (K, N) threshold scheme.
Problem: Storing a private key in one place (server, laptop, wallet) creates a Single Point of Failure. If hacked, lost, or destroyed — entire security is broken.
Example: N=2, K=2
  1. Choose parameters: Large prime P, secret S ∈ [0, P−1], random number R
  2. Create shares: X1 = (S + R) mod P, X2 = (S + 2R) mod P
  3. Reconstruct: (2X1 − X2) mod P = S
Graph-Based Generalization
Place secret at point (0, S). Choose random slope R. Line: y = Rx + S. Any 2 points define the line → get S. Only 1 point → infinite possible lines → no information leaked.
Threshold K Function Type Equation
K = 2 Linear y = Rx + S
K = 3 Quadratic y = R2x² + R1x + S
K = 4 Cubic y = R3x³ + R2x² + R1x + S
Why modulo prime P? Prevents overflow, keeps values bounded, makes reverse-engineering hard — standard in cryptography.
Threshold Cryptography & Multi-Signatures
Threshold Cryptography: Split key material between devices (e.g., desktop + phone). Initiate payment on desktop → partial signature → phone completes signature → broadcast. Key is never reconstructed on any single device.
Multi-Signature: Bitcoin script allows control over an address to be split between different keys. E.g., 3-out-of-4 multisig — three of four co-founders must sign to create a valid transaction.
Comparison

Advantages of Multi-Sig: Keys stored separately → hard for attacker to retrieve 3+. If 1-2 employees go rogue, they can’t take ownership. If one key is lost, funds can still be managed.

Merkle Root & Transaction Ledger
Merkle Root — A single hash value representing all transactions in a block. Transactions are hashed in pairs, combined iteratively, until one top hash remains. Stored in the block header. If even one transaction changes, the Merkle Root changes.
Account-Based vs Transaction-Based Ledger
Account-Based (Not Bitcoin):
• Create, credit, transfer info in ledger
• Must track all account balances
• May need to scan back to genesis to verify
Transaction-Based (Bitcoin UTXO):
• Specify inputs (consumed coins) and outputs (new coins)
• Finite scan for verification
• Each output indexed starting from 0
• No account balance — you own UTXOs
UTXO Key Concepts
  • Change Addresses: Entire output must be consumed — excess sent back to yourself as change
  • Efficient Verification: Scan only between referenced transaction and latest block
  • Consolidating Funds: Multiple inputs can be merged into a single output
  • Joint Payments: Two inputs from different owners → requires two separate signatures

Eventual Consistency & Bitcoin Consensus
Consensus — A procedure through which all peers reach a common agreement about the present state of the distributed ledger. Makes sure every new block is the one and only version of truth agreed upon by all nodes.
Consensus Protocol Objectives
  • Coming to agreement
  • Collaboration and cooperation among nodes
  • Equal rights to every node
  • Mandatory participation of each node
Implicit Consensus
Under random node selection: a random node proposes the next block → other nodes implicitly accept (extend from this block) or reject (extend from previous). No voting protocol needed.
Why Consensus Works Against Attacks
  • Stealing coins: Can’t forge another’s digital signature
  • Denying service: Other honest nodes will include denied transactions
  • Double-spending: Protected by longest-chain rule & 6-confirmation heuristic

SHA-256 in Bitcoin (Detailed)
SHA-256 Compression Function
  1. IV (256 bits): 8 × 32-bit words as initial state
  2. Message Block (512 bits): Input divided into 512-bit blocks
  3. Message Expansion: 512 bits → 64 words × 32 bits = 2048 bits
  4. 64 Rounds: Apply logical functions (AND, XOR, NOT), bit rotations, additions, constants
  5. Final Addition: 8 working variables added back to original IV
  6. Output: 256-bit hash (becomes IV for next block)

Mining Pools
Mining Pool — Group of miners pooling resources to lower variance in rewards. Pool manager distributes revenue proportionally based on each miner’s contributed work (shares).
How Pools Work
  • All miners mine towards the pool manager’s address
  • Revenue distributed based on shares (near-valid blocks)
  • Shares = hashes with many leading zeros but not enough to be valid blocks
  • Rate of shares proves work contribution statistically
Reward Methods
Pay-Per-Share: Flat fee for every valid share. Manager takes all risk. Miners have no incentive to submit valid blocks.
Proportional: Rewards depend on whether pool finds a valid block. Miners still bear some risk. Higher motivation to submit valid blocks.
Pool Hopping: Miners switch between proportional pools (early in cycle when rewards/share are high) and pay-per-share pools (later). Leads to “Pay per last N shares” schemes.
Advantages:
• Predictable income for small miners
• Easier network upgrades
• Lower barrier to entry
Disadvantages:
• Leads to centralization (~4 pools control 50% power)
• Reduces fully validating nodes
• Pool manager becomes single point of influence

Atomic Swaps
Atomic Swap — Cross-chain fair exchange of assets without trusting a central exchange. Uses Hashlock + Timelock. Either BOTH transfers happen, or BOTH refund.

  3. Bob locks Asset B on Chain B (Alice needs ‘s’ to claim, OR Bob refunds after Time B)

Pseudo-anonymity — Users interact via cryptographic addresses (public keys) rather than real identities. While the address itself doesn’t reveal identity, transaction patterns can be analyzed to de-anonymize users. Bitcoin provides pseudo-anonymity.

• Address reuse weakens privacy
• KYC exchanges can reveal identity
Fully Anonymous (Zcash):
• Transactions can be completely shielded
• Sender, receiver, and amount are hidden
• Uses zero-knowledge proofs (zk-SNARKs)

SNARKs & Elliptic Curve Pairing
SNARK = Succinct Non-interactive ARgument of Knowledge. A proof system that is succinct (small proof size), non-interactive (single message), and a sound argument of knowledge.
SNARK Properties
Property Meaning
Succinct Proof is very small (a few hundred bytes) regardless of computation size
Non-interactive Prover sends one message; verifier checks it independently
Argument Computationally sound (not perfectly sound like proofs, relies on cryptographic assumptions)
of Knowledge Prover must actually “know” the witness (secret), not just know that it exists
How SNARKs Work (Simplified)
  1. Setup Phase: Generate public parameters (Common Reference String — CRS) using a trusted setup ceremony
  2. Arithmetic Circuit: Convert the computation/statement into an arithmetic circuit over a finite field
  3. QAP Transform: Convert circuit into Quadratic Arithmetic Program (polynomial equations)
  4. Proof Generation: Prover computes proof using witness (secret input) and CRS
  5. Verification: Verifier checks proof using CRS and public inputs (fast, O(1) operations)
Pairing on Elliptic Curves
Bilinear Pairing — A mathematical function e: G1 × G2 → GT that maps two elliptic curve group elements to a target group element. Key property: e(aP, bQ) = e(P, Q)ab. This enables verification of multiplicative relationships between encrypted values without decryption.
Pairing Properties
  • Bilinearity: e(aP, bQ) = e(P, Q)ab
  • Non-degeneracy: e(P, Q) ≠ 1 for generators P, Q
  • Computability: e(P, Q) can be efficiently computed
Why Pairings Matter for SNARKs: Pairings allow the verifier to check polynomial equations (QAP) on encrypted data. The verifier can confirm that the prover correctly evaluated the polynomial without seeing the actual values.
Zcash & zk-SNARKs for Privacy
Zcash (ZEC) — A privacy-focused cryptocurrency that uses zk-SNARKs to enable fully shielded transactions. Launched in 2016 as a fork of Bitcoin’s codebase. Users can choose transparent or shielded transactions.
Transaction Types in Zcash
Type Sender Receiver Amount
Transparent (t → t) Visible Visible Visible
Shielding (t → z) Visible Hidden Hidden
Deshielding (z → t) Hidden Visible Hidden (partially)
Fully Shielded (z → z) Hidden Hidden Hidden
How zk-SNARKs Preserve Anonymity in Zcash
  1. Note Commitment: When a user receives ZEC, a “note” is created (encrypted) containing value, owner, and randomness
  2. Nullifier: When spending a note, a unique nullifier is revealed (prevents double-spending without revealing which note is spent)
  3. zk-SNARK Proof: The spender generates a proof that:
    • The input notes exist in the commitment tree
    • The nullifiers are computed correctly
    • Input values = output values (conservation)
    • The spender has the spending key
  4. Verification: Miners verify the proof (fast) without learning sender, receiver, or amount
Trusted Setup (Powers of Tau)
zk-SNARKs require a one-time trusted setup to generate parameters. If the secret randomness (“toxic waste”) is not destroyed, fake proofs could be created. Zcash uses a multi-party ceremony (Powers of Tau) — security holds as long as at least one participant honestly destroys their secret.
Advantages of Zcash:
• Full transaction privacy (amount, sender, receiver)
• Selective disclosure for auditors
• Regulatory compliance possible via viewing keys
• Same supply cap as Bitcoin (21M)
Challenges:
• Trusted setup requirement
• Shielded transactions are computationally expensive
• Most users still use transparent transactions
• Regulatory scrutiny due to privacy

Bitcoin: All transactions public, pseudo-anonymous via addresses.

Zero Knowledge Proofs
Zero Knowledge Proof (ZKP) — A cryptographic method by which a prover can demonstrate to a verifier that a statement is true without revealing any additional information beyond the truth of the statement itself.
Three Properties of ZKP
Completeness: If the statement is true, an honest verifier will be convinced by an honest prover.
Soundness: If the statement is false, no dishonest prover can convince an honest verifier (except with negligible probability).
Zero-Knowledge: The verifier learns nothing other than the fact that the statement is true.
Classic Example: Ali Baba’s Cave
  1. A cave has a circular path with a locked door at the back
  2. Prover (Peggy) enters the cave by choosing path A or B randomly
  3. Verifier (Victor) stands outside and calls out which path to return from
  4. If Peggy knows the secret (can unlock the door), she can always emerge from the correct path
  5. After many rounds, Victor is convinced Peggy knows the secret — without ever learning the secret
Types of Zero Knowledge Proofs
Type Interactive? Description
Interactive ZKP Yes Prover and verifier exchange multiple messages; requires both to be online
Non-Interactive ZKP (NIZKP) No Single proof that anyone can verify independently; uses common reference string (CRS)
⭐ Why ZKP Matters for Blockchain
ZKPs enable privacy-preserving transactions on public blockchains. Prove that a transaction is valid without revealing sender, receiver, or amount. Critical for financial privacy and regulatory compliance.

• Keep full nodes accessible

The Ethereum DAO Fork
The DAO (2016) was a decentralized investment fund built on Ethereum. It raised $150M in ETH through an ICO — the largest crowdfunding at the time. A reentrancy vulnerability in its smart contract allowed an attacker to drain ~$60M worth of ETH.
The Attack (June 2016)
  1. The DAO’s smart contract had a reentrancy bug in the withdrawal function
  2. Attacker called the withdrawal function recursively before the balance was updated
  3. Each recursive call drained funds before the contract could deduct the balance
  4. ~3.6 million ETH ($60M) was siphoned into a “child DAO”
The Fork Decision
Pro-Fork (Ethereum — ETH):
• Reverse the theft to protect investors
• Community voted 87% in favor
• “Code is law, but people matter more”
• Hard fork at block 1,920,000
• Funds returned to original investors
Anti-Fork (Ethereum Classic — ETC):
• “Code is law” — no reversal
• Immutability is sacrosanct
• Reversal sets dangerous precedent
• Continued original chain
• Still active today

Denial-of-Service (DoS) Attacks
DoS Attack on a blockchain aims to degrade or disable the network by overwhelming it with spam transactions, exploiting protocol weaknesses, or consuming excessive resources.
Types of DoS Attacks on Blockchain
Attack Type Description Mitigation
Transaction Spam Flood network with low-fee transactions to congest mempool Minimum fee requirements, fee market
Block Bloating Fill blocks with dust transactions to slow down processing Block size limits, dust limits
Eclipse Attack Isolate a node by controlling all its peer connections Diversified peer selection, outbound connections
Resource Exhaustion Exploit computationally expensive operations in smart contracts Gas limits per block and transaction
Sybil-based DoS Create many nodes to overwhelm network messaging PoW/PoS as Sybil resistance
Ethereum Shanghai Attack (2016): Attacker exploited under-priced opcodes (EXTCODESIZE) to slow down the network. Led to gas repricing in the Tangerine Whistle hard fork (EIP-150).
Security in Smart Contracts
Smart contract vulnerabilities can lead to massive financial losses because contracts are immutable once deployed and handle real assets.
Common Vulnerabilities
Vulnerability Description Example
Reentrancy External call before state update allows recursive withdrawal The DAO hack ($60M)
Integer Overflow/Underflow Arithmetic errors when values exceed storage limits BeautyChain (BEC) token
Front-Running Attacker sees pending transactions and inserts own first DEX sandwich attacks
Access Control Missing authorization checks on critical functions Parity wallet freeze ($280M)
Timestamp Dependence Using block timestamp for critical logic; can be manipulated Gambling contracts
Unchecked Return Values Ignoring return values of external calls King of the Ether
Best Practices
  • Checks-Effects-Interactions pattern: Update state before external calls
  • Use SafeMath: Prevent overflow/underflow (built-in since Solidity 0.8)
  • Formal verification: Mathematically prove contract correctness
  • Professional audits: Third-party security review before deployment
  • Bug bounties: Incentivize white-hat hackers to find vulnerabilities
  • Upgradability patterns: Proxy contracts for fixing bugs post-deployment
Scaling & Sharding
Sharding — A technique for horizontal partitioning of the blockchain network. The network is divided into smaller groups (shards), each processing its own transactions and smart contracts in parallel. This multiplies throughput proportionally to the number of shards.
How Sharding Works
  1. Network is divided into N shards, each with its own set of validators
  2. Each shard processes its own transactions independently
  3. A Beacon Chain (or similar coordination layer) manages cross-shard communication and validator assignment
  4. Validators are randomly assigned to shards to prevent collusion
  5. Cross-shard transactions require coordination between source and destination shards
Sharding Challenges
  • Cross-Shard Communication: Transactions spanning multiple shards add latency and complexity
  • Single-Shard Takeover: An attacker needs to compromise only one shard (fewer validators)
  • Data Availability: Ensuring all shard data is available for verification
  • State Synchronization: Keeping global state consistent across all shards
Blockchain Scalability Trilemma
Every scaling solution makes trade-offs: Layer 1 (on-chain) solutions like sharding improve throughput but add complexity. Layer 2 solutions (rollups, channels) offload computation but add trust assumptions. The ideal solution combines both approaches.
Approach Throughput Gain Trade-off
Larger Blocks Linear Centralization (fewer full nodes)
Sharding Proportional to shards Cross-shard complexity, security
Rollups 100-1000x Data availability, withdrawal delays
State Channels Near-infinite (off-chain) Capital lockup, dispute resolution

Kadena
Kadena — A hybrid blockchain platform combining a public PoW chain (Chainweb) with a private permissioned chain (Kuro). Founded by former JP Morgan blockchain team members. Claims to solve the scalability trilemma.
Key Features
  • Chainweb: Public blockchain using braided multi-chain architecture — multiple parallel chains share security through cross-chain Merkle proofs
  • Kuro: Private blockchain for enterprise use, supports up to 8,000 TPS
  • Pact: Human-readable smart contract language with formal verification built in
  • Scalability: Adding more chains increases throughput without sacrificing security
Chainweb Architecture
Chainweb consists of multiple parallel PoW chains that are braided together. Each chain references headers from its peer chains via Merkle proofs. This provides shared security — an attacker must control >50% of ALL chains simultaneously. Throughput scales linearly with the number of chains.

Ripple & Stellar
Ripple (XRP Ledger)
Ripple — A real-time gross settlement system (RTGS), currency exchange, and remittance network. The XRP Ledger uses a consensus protocol called the Ripple Protocol Consensus Algorithm (RPCA) instead of PoW.
  • XRP: Native cryptocurrency; acts as bridge currency for cross-border payments
  • Consensus: Trusted validators reach agreement through iterative voting (80% threshold)
  • Speed: Transactions settle in 3–5 seconds
  • No Mining: All 100 billion XRP were pre-mined at creation
  • Target: Banks and financial institutions (RippleNet)
  • Unique Node List (UNL): Each node trusts a set of validators; must overlap >60%

Rootstock & Drivechain
Rootstock (RSK)
Rootstock (RSK) — A smart contract platform secured by Bitcoin’s hash power through merge mining. It brings Ethereum-compatible smart contracts (Solidity, EVM) to the Bitcoin ecosystem. The native token is RBTC, pegged 1:1 to Bitcoin via a two-way peg.
  • Merge Mining: Bitcoin miners can simultaneously mine RSK blocks at no extra cost
  • EVM Compatible: Supports Solidity smart contracts
  • Bridge (Powpeg): Federated two-way peg between BTC and RBTC
  • Performance: ~30 TPS with 30-second block times
Drivechain (BIP 300/301)
Drivechain — A proposed Bitcoin sidechain mechanism where Bitcoin miners manage the peg between the mainchain and sidechains through Blind Merged Mining. Enables experimentation with new features (smart contracts, privacy, scalability) without modifying Bitcoin’s core protocol.
  • BIP 300 (Hashrate Escrows): Miners vote on sidechain withdrawal requests over ~3-6 month periods
  • BIP 301 (BMM): Sidechain block creation delegated to specialized miners; Bitcoin miners earn fees
  • Goal: Let anyone create sidechains anchored to Bitcoin’s security
  • Controversy: Some argue it gives miners too much power over sidechain funds
Quorum
Quorum — An enterprise-focused Ethereum fork developed by JP Morgan (now under ConsenSys). Designed for permissioned networks requiring high speed, privacy, and confidential transactions.
Key Features
  • Privacy: Private transactions via Tessera (off-chain encrypted transaction manager)
  • Consensus: Supports IBFT (Istanbul BFT), Raft, and QBFT
  • Performance: Higher throughput than public Ethereum (~100–1000 TPS)
  • Permissioned: Node-level and network-level access control
  • EVM Compatible: Full compatibility with Ethereum tooling (Solidity, Web3.js)

Tezos
Tezos (XTZ) — A self-amending blockchain platform with on-chain governance. Stakeholders vote on protocol upgrades directly, avoiding contentious hard forks. Uses Liquid Proof of Stake (LPoS) consensus.
Key Innovations
  • Self-Amendment: Protocol upgrades proposed, voted on, and deployed on-chain without hard forks
  • Liquid PoS (LPoS): Token holders can delegate staking power to “bakers” (validators) without transferring ownership
  • Formal Verification: Smart contracts can be mathematically proven correct (Michelson language)
  • Baking: Validators (“bakers”) need minimum 6,000 XTZ to participate
Governance Process
  1. Proposal Period: Bakers submit protocol upgrade proposals
  2. Exploration Vote: Bakers vote to approve/reject the proposal (80% supermajority needed)
  3. Testing Period: Proposal deployed on testnet for evaluation
  4. Promotion Vote: Final vote to adopt the upgrade (80% supermajority)
  5. Adoption: New protocol activates automatically
MaidSafe & BigchainDB
MaidSafe / SAFE Network
MaidSafe — A decentralized data management and communication network. The SAFE (Secure Access For Everyone) Network aims to create an autonomous, decentralized internet where data is distributed across network nodes without centralized servers.
  • Data Storage: Files are encrypted, broken into chunks, and distributed across the network
  • Self-Encryption: Files encrypted using their own content as the key
  • Proof of Resource: Nodes prove they have storage, bandwidth, and CPU to contribute
  • Safecoin: Native token rewarding nodes for providing resources
  • No Servers: Fully decentralized; no single point of failure or censorship
BigchainDB
BigchainDB — A database solution with blockchain properties: decentralization, immutability, and owner-controlled assets. Combines traditional database performance with blockchain-level trust.
  • High Throughput: Built on distributed databases (MongoDB / RethinkDB)
  • Low Latency: Sub-second finality
  • Asset Management: Native support for creating, transferring, and querying digital assets
  • Permissioned: Typically deployed as a permissioned network
  • Consensus: Uses Tendermint BFT for Byzantine fault tolerance
Storj — Decentralized Cloud Storage
Storj — A decentralized cloud storage platform that leverages unused disk space from network participants worldwide. Files are encrypted, shredded into pieces, and distributed across a global network of nodes.
How Storj Works
  1. Upload: Client-side encryption → file split into 80 erasure-coded pieces
  2. Distribution: Pieces distributed to 80 different storage nodes globally
  3. Redundancy: Only 29 of 80 pieces needed to reconstruct (erasure coding)
  4. Audit: Regular cryptographic audits verify nodes are storing data correctly
  5. Retrieval: Download fastest 29 pieces → reconstruct file → decrypt client-side

🔥 30-Minute Exam Strategy

Priority 1 — Core Concepts (10 min)
  • Blockchain definition: Decentralized, distributed, immutable ledger with cryptographic hashing
  • SHA-256: 256-bit output, 512-bit blocks, 64 rounds, Merkle-Damgård construction
  • Digital Signatures: generateKeys, sign, verify; existential unforgeability
  • UTXO model: Inputs consume, outputs create; immutable coins; change addresses
  • CAP Theorem: Consistency, Availability, Partition Tolerance — pick 2
  • Blockchain Trilemma: Scalability, Security, Decentralization — pick 2
Priority 2 — Consensus & Mining (10 min)
  • PoW: Nonce search, difficulty adjustment every 2016 blocks, 10-min target
  • BFT: 3t+1 minimum nodes; Byzantine Generals Problem
  • Double Spending: GoofyCoin problem → ScroogeCoin → Bitcoin consensus
  • 6 Confirmations: Standard heuristic for transaction finality
  • Mining Hardware: CPU → GPU → FPGA → ASIC evolution
  • Mining Pools: Pay-per-share vs Proportional; pool hopping
Priority 3 — Platforms & Advanced (10 min)
  • Hyperledger: Permissioned, Chaincode, Endorser/Orderer/Committer roles, 6-step TX flow
  • Corda: Privacy-centric, Notary service, States/Contracts/Flows
  • ERC-20: 6 mandatory functions, token explosion (ICOs, DeFi, stablecoins)
  • Smart Contracts: UTXO scripts, 2-of-3 escrow, atomic swaps (hashlock + timelock)
  • zk-SNARKs: Succinct, Non-interactive, uses elliptic curve pairings, Zcash
  • DAO Fork: Reentrancy bug, $60M theft, ETH/ETC split
  • Sharding: Parallel chains, Beacon Chain coordination, cross-shard communication
