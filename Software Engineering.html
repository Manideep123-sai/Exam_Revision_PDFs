Overview of Software Engineering
Process Models, Agile & Waterfall

● Nature of Software

Software is a collection of computer programs, associated data, documentation and procedures. Unlike hardware, software does not wear out but degrades over time due to changes (failure rate follows the "bathtub curve").
Key Characteristics
  • Engineered, not manufactured — developed through design, coding, testing
  • Does not wear out — but degrades due to change requests; failure rate follows Bathtub Curve
  • Bathtub Curve — high initially → stabilises → increases again with changes
  • Complex & Intangible — non-physical product; hard to measure
  • Software = Programs + Data + Documentation
Categories of Software
Category Description Example
System Software Manages computer resources OS, compilers, device drivers
Application Software Solves business problems ERP, payroll, inventory
Engineering/Scientific Number crunching algorithms CAD, simulation software
Embedded Software Controls devices & systems Firmware, IoT devices
Web Applications Network-centric software E-commerce, banking portals
AI Software Pattern recognition, ML Neural nets, chess programs
Open Source Publicly available source code Linux, Firefox, MySQL
⭐ Exam Tip
Software degrades (doesn't wear out). Failure rate = Bathtub curve. Software = Programs + Data + Documentation.
● Software Process & Engineering
Software Engineering is the systematic application of engineering approaches to develop reliable, maintainable software on time and within budget. (IEEE: "systematic, disciplined, quantifiable approach")
Framework Activities (5)
  • Communication — Understand stakeholder requirements; project inception
  • Planning — Define scope, schedule, resources, risks; estimation
  • Modeling — Create analysis and design models (UML, DFD, ERD)
  • Construction — Code generation and testing
  • Deployment — Delivered to customer; support; feedback obtained
Project: Temporary endeavour with defined start/end to achieve a specific goal. Has scope, schedule, budget.
Product: End result of a project — software delivered. Lifecycle: Introduction → Growth → Maturity → Decline.
● Waterfall Model
Waterfall Model is a sequential software development process where progress flows downwards through phases. Each phase must complete before the next begins. Proposed by Winston Royce (1970).
Fig 1.1 — Waterfall Model: Sequential Flow
✅ Advantages
• Simple, linear, easy to manage
• Well-documented phases
• Works for small, well-defined projects
• Easy to schedule milestones
❌ Disadvantages
• Inflexible to changes
• Late error discovery
• No working software until end
• Not for complex/changing requirements
⭐ Exam Tip
Well-defined requirements + no expected changes = Waterfall. Phases: Communication → Planning → Modeling → Construction → Deployment. Winston Royce (1970).
● Prototyping Model
Prototyping Model builds a quick incomplete version (prototype) early to gather user feedback. Refined iteratively until customer approves, then real system is developed.
Fig 1.2 — Prototyping Model: Iterative Feedback Loop
✅ Advantages
• Handles unclear/volatile requirements
• Customer gets early visibility
• Reduces development risk
• Feedback incorporated early
❌ Disadvantages
• Customer may confuse prototype with final product
• Poor documentation
• Developer shortcuts
• May lead to scope creep
● Incremental Model
Incremental Model combines Waterfall's structure with iterative philosophy. Software delivered in builds (increments). Each increment delivers a working, functional piece.
Fig 1.3 — Incremental Model: Multiple Working Builds
✅ Advantages
• Working software delivered early
• Higher-priority features first
• Lower risk with early feedback
• Easier to test each increment
❌ Disadvantages
• Requires good requirements partitioning
• Architecture must be defined upfront
• Integration issues between increments
● Spiral Model
Spiral Model (Barry Boehm, 1988) combines iterative development with systematic risk assessment. Each cycle passes through four quadrants. The only model that explicitly addresses risk.
Fig 1.4 — Spiral Model: 4-Quadrant Risk-Driven Approach
Quadrant Activity Output
1. Planning Define objectives, alternatives, constraints Project plan, cost estimate
2. Risk Analysis Identify & analyse risks, build prototype Risk mitigation plan, prototype
3. Engineering Design, code, test software Working software increment
4. Evaluation Customer evaluates, plans next iteration Customer feedback, next iteration plan
⭐ Exam Tip
Spiral = RISK-DRIVEN. "Which model explicitly addresses risk?" → Spiral. Barry Boehm 1988. Each pass = one spiral loop. Risk decreases toward center. Cost increases outward.
● Agile Process & Extreme Programming (XP)
Agile is an iterative and incremental approach emphasising flexibility, collaboration, customer involvement, and rapid delivery. Based on the Agile Manifesto (2001).
Agile Manifesto — 4 Core Values
We value MORE:
✦ Individuals & interactions
✦ Working software
✦ Customer collaboration
✦ Responding to change
Over (still valued but less):
○ Processes & tools
○ Comprehensive documentation
○ Contract negotiation
○ Following a plan

● Umbrella Activities
Umbrella Activities apply across ALL phases of the software process throughout the entire lifecycle — NOT just at specific phases.
  • Software Project Tracking & Control — Monitor progress against plan; take corrective action
  • Risk Management — Identify, assess, and mitigate risks throughout
  • Software Quality Assurance (SQA) — Ensure process quality throughout
  • Technical Reviews — Walkthroughs, inspections to find errors early
  • Measurement — Collect & analyse process and product metrics
  • Software Configuration Management (SCM) — Manage changes to work products
  • Reusability Management — Define criteria and manage component reuse
  • Work Product Preparation & Production — Documentation, models, forms
💡 Key Insight: Umbrella activities are NOT sequential — they happen THROUGHOUT the entire lifecycle, overlapping with all framework activities.

● COCOMO Model
COCOMO (Constructive Cost Model) — empirical model by Barry Boehm (1981). Predicts Effort (person-months), Development Time, and Staff size from KLOC.
Three Software Modes
Mode Characteristics a b c d
Organic Small team, familiar, stable requirements 2.4 1.05 2.5 0.38
Semi-Detached Medium team, mixed experience 3.0 1.12 2.5 0.35
Embedded Tight constraints, high reliability needed 3.6 1.20 2.5 0.32
Effort (E) = a × (KLOC)^b   [Person-Months]
Development Time (T) = 2.5 × E^d   [Months]
Staff (S) = E / T   [Persons]
⭐ Worked Numerical Example
Problem: Software product = 32,000 LOC, Semi-Detached mode. Find Effort, Time, Staff.

Given: KLOC=32, a=3.0, b=1.12, c=2.5, d=0.35

Step 1: E = 3.0 × (32)^1.12 = 3.0 × 48.94 ≈ 146.8 PM
Step 2: T = 2.5 × (146.8)^0.35 = 2.5 × 6.66 ≈ 16.65 Months
Step 3: S = 146.8 / 16.65 ≈ 9 Persons
Intermediate COCOMO — 15 Cost Drivers (EAF)
E = a × (KLOC)^b × EAF   (EAF = product of 15 cost driver ratings)
Category Cost Drivers
Product RELY (reliability), DATA (database size), CPLX (complexity)
Computer TIME (execution time), STOR (storage), VIRT, TURN
Personnel ACAP (analyst capability), AEXP, PCAP, VEXP, LEXP
Project MODP (modern programming), TOOL, SCED (schedule)

● Function Points (FP)
Function Points measure functionality independent of programming language. Developed by Allan Albrecht (IBM, 1979).
Component Description Simple/Avg/Complex
External Inputs (EI) User inputs that update internal files 3 / 4 / 6
External Outputs (EO) Outputs to user (reports, screens) 4 / 5 / 7
External Inquiries (EQ) Input+output combination (no update) 3 / 4 / 6
Internal Logical Files (ILF) Internal data files maintained 7 / 10 / 15
External Interface Files (EIF) Files referenced from other systems 5 / 7 / 10
UFP = Σ(count × weight) for all 5 components
FP = UFP × [0.65 + 0.01 × Σ(Fi)]   where 14 complexity factors Fi each rated 0–5
● WBS, Milestones & Deliverables
WBS (Work Breakdown Structure) is a hierarchical decomposition of total project scope into smaller, manageable work packages.
Milestone: Significant event/checkpoint. Has NO duration (point in time). E.g., "Requirements approved."
Deliverable: Tangible output/product with a due date. E.g., "SRS Document submitted."
Feature Milestone Deliverable
Nature Event / checkpoint Product / output
Duration Zero (point in time) Has delivery date
Purpose Track progress Provide value to stakeholders
● CPM & PERT
CPM — Deterministic. Single time estimate. Critical path = longest path = minimum project duration. Critical path activities have zero float.
Float = Late Start − Early Start
Critical Path Float = 0
PERT — Probabilistic. Three time estimates: Optimistic (O), Most Likely (M), Pessimistic (P).
Expected Time (te) = (O + 4M + P) / 6
Variance = [(P − O) / 6]²
Feature CPM PERT
Time estimate Single deterministic Three estimates (O,M,P)
Type Deterministic Probabilistic
Used for Well-defined activities R&D, uncertain projects
Focus Cost-time trade-off Time uncertainty
● Risk Management
Risk Management identifies, assesses, and controls threats to a software project. Risk = Probability × Impact.
  1. Risk Identification — Identify potential risks via checklists, brainstorming
  2. Risk Analysis — Estimate probability and impact of each risk
  3. Risk Prioritization — Rank risks by exposure (RE = P × C)
  4. Risk Planning — Define avoidance, mitigation, contingency plans
  5. Risk Monitoring — Track identified risks throughout project
Risk Exposure (RE) = P(risk) × C(risk)   [Probability × Cost/Impact]
Risk Type Description Example
Project Risks Threaten schedule, budget, resources Staff turnover, budget cuts
Technical Risks Threaten quality or timeliness Unproven algorithm, new tech
Business Risks Threaten viability of the software Market shift, competitor product
● RMMM Plan
RMMM Plan (Risk Mitigation, Monitoring, and Management) documents all risk analysis work. Used as part of the overall project plan.
Component Description Timing
Risk Mitigation Proactive steps to reduce probability/impact BEFORE risk occurs Before risk occurs
Risk Monitoring Continuously track risk indicators; check if mitigation is working Throughout project
Risk Management Contingency plan — what to do IF the risk actually occurs (reactive) After risk occurs

● Requirements Engineering Process
Requirements Engineering (RE) is a systematic process of eliciting, documenting, analysing, and managing software requirements to ensure the system meets stakeholder needs.
Fig 3.1 — Requirements Engineering Process
● Functional vs Non-Functional Requirements
Functional Requirements define WHAT the system should DO — services, functions, behaviors.
  • User authentication (login/logout)
  • Search and filter products
  • Generate monthly reports
  • Process online payments
Non-Functional Requirements define HOW the system performs — quality attributes and constraints.
  • Performance — Response < 2 seconds
  • Reliability — 99.9% uptime
  • Security — Encrypted data
  • Scalability — 10,000 concurrent users
  • Usability — Learnable in 1 hour

● SRS (Software Requirements Specification)
SRS is a formal document describing complete requirements. Serves as contract between developers and customers. Based on IEEE 830 standard.
Structure (IEEE 830)
  1. Introduction — Purpose, scope, definitions, overview
  2. Overall Description — Product perspective, functions, user characteristics, constraints
  3. Specific Requirements — Functional, non-functional, external interface requirements
  4. Appendices + Index
Characteristics of a Good SRS
Quality Description
Correct Accurately reflects actual needs
Unambiguous Only one interpretation possible
Complete All requirements included
Consistent No contradictions between requirements
Ranked Each requirement has priority/stability indicator
Verifiable Can be tested to confirm it's met
Modifiable Structure allows easy changes
Traceable Origin known; forward and backward traceability

Software Design Concepts
Architecture, Cohesion & Coupling
● Design Concepts & Principles (All 9)
# Concept Definition Example
1 Abstraction Focus on essential features; ignore irrelevant details. Data abstraction = abstract data types. Procedural abstraction = named instruction sequence. Stack: push/pop hide array logic
2 Architecture Overall structure of software components and how they interact. Defines the system at the highest level. MVC, Client-Server, Microservices
3 Patterns Reusable solutions to commonly occurring design problems. Singleton, Observer, Factory
4 Modularity Dividing software into separate, independently manageable modules. Reduces complexity. Login module, Payment module
5 Information Hiding Each module hides its internal details. Only expose necessary interface. Private variables with getters/setters
6 Functional Independence Each module does ONE specific thing (high cohesion + low coupling). Module that ONLY handles authentication
7 Refinement (Stepwise) Progressively elaborate design from high-level to detailed. Opposite of abstraction. Program structure → function details → code
8 Refactoring Improve code structure WITHOUT changing observable behavior. Eliminates technical debt. Remove duplicate code, extract method
9 Design Classes Translate analysis model to design model. 5 types: User Interface, Business Domain, Process, Persistent, System. CustomerAnalysis → CustomerDAO + CustomerUI
● Cohesion Types — All 7 Ranked
Cohesion measures how closely related and focused a single module's responsibilities are. HIGH cohesion = GOOD.
Fig 4.1 — Cohesion Types: Ranking (Best → Worst)
1. Functional ⭐ BEST
Single well-defined function
2. Sequential
Output of one → input of next
3. Communicational
Same data, different operations
4. Procedural
Functions execute in sequence
5. Temporal
Activated at same time
6. Logical
Same logical category
7. Coincidental ❌ WORST
No meaningful relationship
Type Description Example
Functional All elements contribute to a single well-defined function Compute_Square_Root()
Sequential Output of one activity is input to next (pipeline) Read_Data → Parse → Write_Results
Communicational All elements operate on same input data Get_Customer_Name_And_Address()
Procedural Elements related by order of execution Open_File(), Read_Data(), Close_File()
Temporal Elements activated at the same time Initialization module (startup routines)
Logical Elements belong to same logical class, different purposes All_IO_Operations()
Coincidental Elements have no meaningful relationship — arbitrary grouping Miscellaneous_Functions()
● Coupling Types — All 6 Ranked
Coupling measures the degree of interdependence between modules. LOW coupling = GOOD. Goal: minimize coupling, maximize cohesion.
Fig 4.2 — Coupling Types: Ranking (Best → Worst)
1. No Coupling ⭐ BEST
Independent modules
2. Data Coupling
Share simple data via params
3. Stamp Coupling
Share composite data structure
4. Control Coupling
One passes flag to control another
5. Common Coupling
Share global data
6. Content Coupling ❌ WORST
One modifies internals of another
Type Description Example
Data Coupling Communicate through simple data parameters only calcTax(income, rate)
Stamp Coupling Share a composite data structure (struct/object) processCustomer(customerRecord)
Control Coupling One passes a flag to control behavior of another processData(flag=true)
External Coupling Rely on same external I/O format or protocol Both modules read same CSV format
Common Coupling Both read/write shared global data Global config variable
Content Coupling One module directly accesses internals of another Module A changes private var in Module B
⭐ Exam Tip — High-Value!
Cohesion = single module focus → HIGH = GOOD → F-S-C-P-T-L-C (Functional best, Coincidental worst)
Coupling = module interdependence → LOW = GOOD → D-S-C-E-C-C (Data best, Content worst)

M5 Validation & Verification (Testing)
● Testing Fundamentals & V&V
Verification — "Building product RIGHT?" Checks conformance to specification. Process-oriented. Uses: reviews, inspections, walkthroughs. Done by developers.
Validation — "Building RIGHT product?" Checks customer needs are met. Product-oriented. Uses: testing (unit, integration, system, UAT). Done by testers/customer.
4 Levels of Testing
Level What is Tested Who Goal Method
Unit Testing Individual functions/modules Developer Verify each unit works in isolation White Box
Integration Testing Combined modules/subsystems Developer/Tester Verify interfaces between modules Both
System Testing Complete integrated system Test team Verify system meets all requirements Black Box
Acceptance Testing (UAT) Final system from user perspective Customer Verify system meets business needs Black Box
● Black Box Testing — BVA & Equivalence Partitioning
Black Box Testing tests external behaviour WITHOUT knowledge of internal implementation. Based on requirements/specifications. Also called: Behavioural, Specification-Based Testing.
Equivalence Partitioning (EP)
Divide inputs into partitions where all values are treated identically. Select ONE representative from each.

Example — Age (valid: 18–56):
• Partition 1 (Invalid): age < 18 → test: 5  |  Partition 2 (Valid): 18–56 → test: 30  |  Partition 3 (Invalid): age > 56 → test: 70
Boundary Value Analysis (BVA)
BVA tests AT and AROUND boundaries where errors are most likely. For range [min,max]: test min–1, min, min+1, nominal, max–1, max, max+1 (7 test cases).
Fig 5.1 — BVA: Valid Range 18–56
TC Input Type Expected Result
TC1 17 min – 1 (invalid boundary) Error: Invalid age
TC2 18 min (valid boundary) Accepted as valid
TC3 19 min + 1 (just inside) Accepted as valid
TC4 37 Nominal (midpoint) Accepted as valid
TC5 55 max – 1 (just inside) Accepted as valid
TC6 56 max (valid boundary) Accepted as valid
TC7 57 max + 1 (invalid boundary) Error: Invalid age
● White Box Testing
White Box Testing (Glass Box / Structural / Clear Box) examines the internal code structure. Tester needs full knowledge of implementation.
Coverage Type Description Strength
Statement Coverage Every statement executed at least once Weakest
Branch Coverage Every branch (TRUE and FALSE) tested Stronger
Condition Coverage Each boolean sub-expression tested true AND false Stronger
Path Coverage Every possible execution path tested Strongest (impractical for large programs)
● Cyclomatic Complexity
Cyclomatic Complexity (M) — developed by Thomas McCabe (1976). Measures number of linearly independent paths through source code. Determines minimum test cases for full path coverage.
Three Equivalent Formulas
Method 1: M = E − N + 2P   (E=Edges, N=Nodes, P=connected components; P=1 for single program)
Method 2: M = Number of regions in the flow graph (including outer region)
Method 3: M = Number of predicate nodes + 1   (Predicates = IF, WHILE, FOR, CASE, etc.)
Fig 5.2 — Control Flow Graph & Cyclomatic Complexity
M Value Risk Level Recommendation
1 – 10 ✅ Low Risk Simple, well-structured code
11 – 20 ⚠ Moderate Risk Manageable but monitor
21 – 50 🔴 High Risk Complex — consider refactoring
> 50 💀 Very High Risk Untestable — refactor immediately

SCM, Re-engineering & Reuse
● Software Maintenance Types
Software Maintenance is modification of software after delivery to correct faults, improve performance, or adapt to changed environment. Accounts for 60–70% of total software lifecycle cost.
Type Purpose Triggered By Example % Cost
Corrective Fix bugs/errors after deployment Error reports from users Fix login crash bug ~17%
Adaptive Adapt to new environment (OS, hardware, law) Environmental change Update for new OS version ~20%
Perfective Improve performance or add new features User requests, competition Add search functionality ~60%
Preventive Prevent future problems; restructure code Code quality degradation Refactor spaghetti code ~3%
💡 Perfective dominates at ~60% — most maintenance is enhancements, not just bug fixes.
● Software Configuration Management (SCM)
SCM manages change throughout the software lifecycle. Identifies, controls, audits, and reports changes to software products.
SCM Activity Description
Configuration Identification Identify and label all CIs: source code, docs, data, test cases
Version Control Track and manage multiple versions; maintain change history
Change Control Formal process: request → evaluate → approve → implement → test
Configuration Auditing Verify built configuration matches specification
Status Reporting Record and report status of all changes
Build Management Automate building software from source code
Version Control: Git, SVN, Mercurial  |  Build: Maven, Gradle, Ant
CI/CD: Jenkins, GitLab CI, GitHub Actions  |  Issue Tracking: JIRA, Bugzilla, GitHub Issues
● Re-engineering (6 Steps)
Re-engineering examines and alters an existing system to reconstitute it in a new form. Goal: improve quality and maintainability of legacy systems without full rebuild.
  1. Inventory Analysis — Identify all components; assess which need re-engineering
  2. Document Restructuring — Update and improve existing documentation
  3. Reverse Engineering — Recover design from existing code
  4. Code Restructuring — Refactor without changing behavior
  5. Data Restructuring — Redesign data architecture (databases)
  6. Forward Engineering — Recreate system with recovered design + modern technology
● Reverse Engineering & Comparison
Reverse Engineering analyses existing software to identify components and relationships. Recovers design FROM code — opposite direction of forward engineering.
Feature Reverse Engineering Re-engineering
Goal Understand existing system Improve / transform existing system
Output Design/requirements documentation New, improved working system
System changes? No — analysis only Yes — system is changed/rebuilt
Direction Code → Design (backward) Full cycle including forward engineering
Relationship Step 3 of re-engineering Broader process that includes reverse engineering
● Software Reuse
Software Reuse uses existing artifacts to build new systems. Goal: reduce cost, time, and effort while improving quality.
Reuse Level Description Example
Code Reuse Reuse functions, classes, modules Standard libraries
Design Reuse Reuse design patterns, architectures MVC pattern, Singleton
Requirement Reuse Reuse specifications from similar projects Authentication requirements
Component Reuse Reuse complete tested components Third-party APIs, SDKs
Application Reuse (COTS) Configure existing commercial software SAP ERP, Salesforce CRM
✅ Benefits
• Reduced development time/cost
• Higher reliability (already tested)
• Faster time-to-market
• Consistent standards
❌ Challenges
• Components may not fit perfectly
• Dependency on third-party
• Security risks
• Documentation overhead

● QA vs QC
QA (Quality Assurance) — Process-oriented. PREVENTS defects by improving development processes. Proactive. Entire SDLC.
QC (Quality Control) — Product-oriented. DETECTS defects in finished product. Reactive. Testing phase.
Feature QA QC
Focus Process Product
Approach Proactive — prevent defects Reactive — detect defects
Scope Entire SDLC Testing phase mainly
Goal Build quality into the process Find and remove defects
Activities Process audits, reviews, standards Testing, inspection, walkthroughs

Six Sigma eliminates defects through data-driven methodology. 6σ = 3.4 defects per million opportunities (DPMO). Motorola (Bill Smith, 1986), popularised by GE (Jack Welch).

● CMM & CMMI Levels
CMM (Capability Maturity Model) — SEI, Carnegie Mellon (1991). Assesses process maturity on 5 levels. CMMI (2002) is the successor.
Fig 7.2 — CMM 5 Levels Pyramid
Level Name Key Characteristic Key Process Areas
1 Initial Ad hoc, chaotic; success depends on heroics None defined
2 Repeatable/Managed Basic PM; repeat successes on similar projects Requirements Mgmt, Project Planning, QA, SCM
3 Defined Org-wide standard documented process; tailored per project Training, Peer Reviews, SW Product Engineering
4 Quantitatively Managed Metrics collected; process statistically controlled Quantitative Process Mgmt, SW Quality Mgmt
5 Optimizing Continuous improvement; technology innovation Defect Prevention, Process Change Management
⭐ Exam Tip
Memory trick: "I Really Define Quantitative Optimization" = Initial, Repeatable, Defined, Quantitative, Optimizing. Level 2=Managed. Level 3=Defined (most orgs target this).

● Product & Process Metrics
Product Metrics measure software product characteristics: quality, size, complexity.
  • LOC — Lines of Code
  • Function Points — Functional size
  • Cyclomatic Complexity — Code complexity
  • Defect Density — Bugs per KLOC
  • CK Metrics — OO metrics (WMC, DIT, NOC, CBO, RFC, LCOM)
Process Metrics measure development process effectiveness and efficiency.
  • DRE — Defect Removal Efficiency
  • Productivity — FP or LOC per person-month
  • Cost Per Defect — Total cost / total defects
  • Review Coverage — % of work reviewed

Feature Agile Waterfall

Scenario Best Model Key Reason
